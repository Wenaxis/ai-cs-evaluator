# 怎么验证：四层，从免费到花钱

> 这份文档回答一个问题：**「你说改好了，凭什么信？」**
>
> 面试官会问，将来的你自己也会问。项目跑出 96.7% 那天，我心里其实没底 ——
> 因为同一个 96.7% 至少有三种解释：改动真有用 / 这个模型本来就行 / 量表太松。
> 光看分数分不出是哪一种。
>
> 下面四层，按「便宜 → 贵」排，也按「必须 → 加分」排。

---

## 零、先把「验证」拆开

「验证改好了」其实是三件不同的事，混在一起做会乱：

| 要验证的 | 问题 | 用哪层 | 花钱 |
|---|---|---|---|
| **A. 代码状态** | 我以为的代码，真的是在跑的那份吗？ | 第一层 | 0 |
| **B. 效果** | 回答变好了吗？好在哪？ | 第二层、第三层 | 0 / 几毛 |
| **C. 因果** | 变好是因为这个改动，还是碰巧？ | 第四层 | 几毛 |

**顺序不能倒。** 我一开始想直接跑第四层（控制变量），跑到一半发现自检脚本报错 ——
`exclude_id` 那行注释和行为对不上。如果没先做 A，第四层的两组实验都是在错的代码上做的，
结论再漂亮也是废的。

## 第一层：静态自检（0 元，3 秒）

不联网、不调模型，只检查「代码是不是我以为的那样」。

```bash
.venv/Scripts/python.exe scripts/selfcheck.py
```

实测输出：

```

不联网、不花钱、几秒跑完。全过了再去跑真评测。

      OK   30 条问题都能检索到规则：命中率 30/30

      OK   search_knowledge 已注册

结论：18/18 项通过
```

### 这一层真的抓到过东西

第一次跑，第 5 项是 **FAIL**。翻代码：

```python
exclude_id: int | None = None,     # ← 有默认值
"""exclude_id 必须由调用方显式传入。
这里不给默认值，就是为了让「忘了防泄漏」这件事在代码上不可能发生。"""   # ← 注释在说谎
```

注释信誓旦旦说「不给默认值」，签名上老老实实给了 `= None`。
两者都没错到会崩，但**那句注释是假的** —— 而防泄漏是这套评测能不能信的地基。
如果有人照着注释的承诺写调用，忘了传，答案泄漏，分数会好看得离谱，还没有任何报错。

已经修了：把 `exclude_id` 挪到 `k` 前面，去掉默认值。现在真忘了传，直接 `TypeError`。
37 个测试全过（所有调用点本来就用关键字传，没受影响）。

**这就是这一层的价值**：它抓的不是 bug，是「我以为」和「实际」的缝。

## 第二层：看回答原文（0 元，5 分钟）

分数是压缩过的。压缩会丢信息，而且丢的正好是你最想知道的那些。

```bash
.venv/Scripts/python.exe scripts/show_answer.py --id 7,25
```

`--id` 后面可以写多条，也可以换成：

- `--fail`：只看 Agent 答偏的
- `--diff`：只看「原客服答偏 → Agent 答对」和「原客服答对 → Agent 答偏」的

### 一条答得好的

```
====================================================================
#7  提现要收手续费吗
--------------------------------------------------------------------
原客服：答对   Agent：答对
打分：5    过程标签：无
判词：明确回答不收手续费，并给出资金来源分档与特殊情形口径
退出：answered   轮数：2
工具：search_knowledge(提现要收手续费吗)
--------------------------------------------------------------------
**不收手续费。** 余额提现免费：从银行卡转入的资金提现回原卡不收费，余额内其他来源资金提现同样免费。

只有超出免费额度、跨行加急等特殊情形可能收费，具体以提现页面展示的收费提示为准。
```

看三样东西，逐条对：

| 该有的 | 这里有没有 |
|---|---|
| 结论先行 | 有，「**不收手续费。**」加粗在第一句 |
| 分档口径 | 有，按资金来源分「银行卡转入 / 其他来源」 |
| 例外情形 | 有，「超出免费额度、跨行加急」并指向页面提示 |

这条在 v2 里是纯靠猜的（判例库检索回「关闭自动续费 / 换绑手机号 / 退款没收到」，
一条都不相关），现在第一句就答准了。

### 一条答坏的（而且是唯一一条）

```
====================================================================
#25  转人工客服要怎么操作
--------------------------------------------------------------------
原客服：答对   Agent：答偏   ⚠️ 弄坏了
打分：1    过程标签：skipped_retrieval, unanswered_core
判词：只给转人工入口，未给具体操作路径，属答非所问
退出：answered   轮数：1
工具：（没调工具）
--------------------------------------------------------------------
转人工可以直接在这里帮你转，不用你自己操作。
```

**「（没调工具）」+「轮数：1」。**

它一轮就答了，压根没查知识库。而第一层那张表里，`#25 → 如何转人工客服` 检索得分 **48.39**，
排在全库中上 —— 知识库里明明有这条规则，只要查一下就能照着答。

所以这条的失败**不是检索能力问题，是它跳过了检索**。为什么跳？因为在它的自我认知里，
「转人工」是它自己的动作，不需要查资料。这是个很典型的 Agent 失败模式：
**工具在手上，但它判断「这次不用」**。

> 这条比「检索不到」更值得记住。检索不到是能力上限，能查到却不查是判断失误 ——
> 后者更难发现，因为所有指标都不报错，只有把工具链打出来才看得见。

如果想看被它修好的那几条，`--diff`（下面是压缩摘要，实际会打出完整回答和工具链）：

```
#1   转账转错了能退回来吗          原客服：答偏   Agent：答对   ✅ 修好了
#16  手机号注销了怎么换绑          原客服：答偏   Agent：答对   ✅ 修好了
...
#25  转人工客服要怎么操作          原客服：答对   Agent：答偏   ⚠️ 弄坏了
```

## 第三层：重跑复现（约 0.1 元，3 分钟）

前两层证明「代码对、回答读得下去」。这一层证明「换一次跑，还是这个结果」。

```bash
# 1. 跑 30 条，产出 output/traces.json 和 agent_metrics.json
.venv/Scripts/python.exe -m src.eval.runner

# 2. 让评测 Agent 逐条打分（读 traces.json）
.venv/Scripts/python.exe -m src.eval.judge

# 3. 算绝对质量（读上两步的输出）
.venv/Scripts/python.exe -m src.eval.report_v3
```

参考耗时（deepseek-chat / 30 条）：`runner` 约 82 秒，`judge` 约 41 秒。
token 消耗：runner 约 9.2 万 input + 1.5 万 output，折合人民币一毛出头。

第 3 步的关键输出应该长这样（下面是实测原文）：

```
================================================================
[M8+] Agent 应答质量报告（不与原客服对齐，看绝对质量）
================================================================

用例数                30

应答质量
  Agent 答对          29 条（96.7%）
  原客服答对          21 条（70.0%）
  差值                +26.7 个百分点

逐条对比
  原答偏 → Agent 答对（修好的）   9 条 [1, 5, 8, 16, 18, 19, 22, 23, 24]
  原答对 → Agent 答偏（弄坏的）   1 条 [25]
  两边都答对                      20 条
  两边都没答对                    0 条 []

质量风险
  编造信息            0 条
  未答核心            1 条 [25]
  转人工              0 条

过程
  知识库使用率        96.7%（29 条）
  判例库使用          6 条
  平均轮数            1.97
  工具成功率          100.0%
```

### 数字对不上怎么办

按这个顺序查，别跳：

1. **Agent 答对明显少于 25** → 先回第一层跑 `selfcheck.py`。八成是知识库没加载（对照第四层的结果：没知识库只有 13.3%）。
2. **工具成功率不是 100%** → 看 `output/traces.json` 里 `ok: false` 的那几步的 `error` 字段。工具报错而 Agent 装作成功，是另一类问题。
3. **转人工数量 > 5** → prompt 的兜底准则吞掉了正常回答。可能模型换了、或者知识库检索阈值被改了。
4. **编造 > 0** → 有题目知识库没覆盖，模型在补。去 `cs_rules.json` 里补那条。
5. **平均轮数 > 2.5** → 检索没命中，Agent 在多轮试错。跑 `selfcheck.py --table` 看是哪几条。

### 一个必须知道的坑

`scripts/mock_run.py` 会**覆盖** `output/traces.json`（它是离线冒烟测试，用假模型）。
别在两轮真评测之间跑它，否则你比对的是「真数据 vs 假数据」，而且看不出来。

## 第四层：控制变量（最硬，约 0.1 元，5 分钟）

前三层证明「它确实答得不错」。这一层证明「不错是因为我加的那个东西」。

做法：**只动一个变量**，把知识库文件移走，别的什么都不改。

```bash
# 移走知识库
mv data/knowledge/cs_rules.json data/knowledge/cs_rules.json.bak

# 先确认真的禁掉了（不然跑到一半才发现没禁，白花钱）
.venv/Scripts/python.exe -c "from src.agent.knowledge import KnowledgeBase; KnowledgeBase()"
# 期望：FileNotFoundError

# 重跑
.venv/Scripts/python.exe -m src.eval.runner
.venv/Scripts/python.exe -m src.eval.judge
.venv/Scripts/python.exe -m src.eval.report_v3

# 恢复（别忘了）
mv data/knowledge/cs_rules.json.bak data/knowledge/cs_rules.json
```

### 结果

| 指标 | 有知识库 | 拿掉知识库 | 变化 |
|---|---|---|---|
| **Agent 答对** | **29 / 30（96.7%）** | **4 / 30（13.3%）** | −25 条 |
| 转人工 | 0 | **24 条（80%）** | +24 |
| 未答核心 | 1 | **25** | +24 |
| 工具成功率 | 100% | **64.6%** | −35.4pt |
| 平均轮数 | 1.97 | **3.5** | +1.5 |
| 修好 / 弄坏 | 9 / 1 | 2 / **19** | — |
| 编造信息 | 0 | 2 | +2 |

**96.7% → 13.3%。** 同一份代码、同一个模型、同一句 prompt，只差一个 JSON 文件。

### 掉下去的过程更说明问题

缺了知识库之后，Agent 并没有摆烂 —— 29 条用例里它尝试检索 29 次，每次都失败，
错误原文一样：

```
知识库未加载
```

然后它的行为链条是：

1. 查知识库 → 失败
2. 改查判例库 → 查得到，但判例只有「这题该怎么答」的叙述，没有事实口径
3. prompt 说「不要凭常识编」→ 它守住了
4. prompt 说「查不到就转人工」→ 24 条转人工

**这不是能力退化，是数据供给断了之后，一个诚实的 Agent 唯一能做的事。**

### 顺手抓到的指标 bug

跑完第一版对照，`agent_metrics.json` 里写着：

```
知识库使用率        96.7%（29 条）
```

**知识库文件已经移走了，使用率还是 96.7%。**

原因：原来统计的是「这条会话的 `tool_names` 里有没有 `search_knowledge`」——
`tool_names` 只记调用过什么，不记成功没有。Agent 每轮都尝试查、每次失败，名字还是进了列表。

已改成只数成功的（`src/eval/runner.py` 的 `_used_ok()`）。新口径下：

| 组 | 知识库成功调用 | 判例库成功调用 |
|---|---|---|
| v3（有知识库） | 29 | 6 |
| 无知识库 | **0** | 29 |
| v2 原版（还没知识库） | 0 | 29 |

这个 bug 是这一层唯一真正的产出，而且它比实验结论更重要：
**一个只会涨的指标，比没有指标更危险。** 它不报错、不告警，只在你想验证自己没错的时候，
告诉你「你没错」。

## 总结成一张表

| 层 | 命令 | 花多久 | 答什么问题 | 通过标准 |
|---|---|---|---|---|
| 一 | `selfcheck.py` | 3 秒 | 代码是不是我以为的 | 18/18 |
| 二 | `show_answer.py --id 7,25` | 5 分钟 | 回答读得下去吗 | 结论先行 + 分档 + 例外，三样齐 |
| 三 | `runner` → `judge` → `report_v3` | 3 分钟 | 结果稳不稳 | 答对 ≥ 28，编造 0，工具 100% |
| 四 | `mv` 知识库 + 重跑 | 5 分钟 | 是不是因为这个改动 | 掉到 13% 左右，即证明因果成立 |

四层都过，才能说「这个项目我讲得清」。只过前三层，只能说「它跑起来效果不错」——
这两句话在面试里的分量差很远。

## 还差一层：没验的那部分

诚实起见，写清楚哪些**没有**被验证：

**1. 知识库本身对不对。**
这 30 条规则是我从实测记录里提炼的。如果提炼时把某条口径写错了，Agent 会自信地答错，
而上面所有指标都看不出来 —— 它们只测「Agent 有没有照着知识库答」，不测「知识库对不对」。
要验这个，得拿真实客服文档逐条对。这是另一件事，没做。

**2. 量表本身的可靠性。**
`judge` 也是大模型。它给 5 分，不代表这条真的是 5 分。
已知的坑：第 28 条曾经同时拿到「5 分」和 `fabricated_info=true` ——
打分链和过程标记链是两条独立的判断，会打架。
更彻底的做法是人工复核 20 条算 judge 与人的 Kappa。没做。

**3. 6 条多轮用例从没执行过。**
`build_all()` 定义了 36 条，`runner` 只读 `records.json` 的 30 条。这条路是断的。

**4. 真实流量下的表现。**
30 条是人工挑的、干净的、单轮的。真实用户会打错字、会一次问三件事、会中途改主意。
这些一概没测。

## 面试怎么讲这一段（40 秒版）

> 「跑出 96.7% 的时候我没敢直接信。因为同一个数字至少有三种解释：改动有用、
> 模型本来就行、量表太松。
>
> 所以我做了三件事：先写了个不花钱的自检脚本，确认代码状态 —— 它当场抓到我一个注释和签名打架的地方；
> 然后把回答原文逐条读了一遍，发现唯一答坏的那条不是检索不到，是它压根没查；
> 最后把知识库文件移走重跑了一遍 —— 同一个模型、同一句 prompt，答对率从 96.7% 掉到 13.3%，
> 24 条转人工。这才敢说是知识库起的作用。
>
> 顺带还抓到一个指标 bug：知识库都移走了，使用率还显示 96.7%。因为统计算的是『调过』不是『成功』。
> 这件事让我后面所有指标都改了口径。」
