# 上手与阅读指南

> 这份文档写给第一次读这个项目的人 —— 也就是三天后的你自己。
>
> 目标只有一个：让你从「能跑起来」走到「能讲清楚每一块在干什么」。
>
> **读法建议**：不要从第一行读到最后一行。先照第一节把项目跑起来，
> 跑通了再按第三节的顺序读代码。跑不通就先别读代码 —— 读也读不进去。

## 一、五分钟跑起来（不需要任何 API Key）

这一步的目的不是「跑出结果」，而是**确认你的环境和代码都没问题**。
做完这一步，你就能确定：如果后面报错，那一定是 Key 或网络的问题，不是代码的问题。
这能省掉你大量的排查时间。

### 1.1 装依赖

打开终端，进到项目目录（就是有 `README.md` 和 `requirements.txt` 的那一层）：

> **用 PowerShell 的话，先跑这一行**，否则后面所有中文输出都是乱码。
> 实测 `chcp 65001` 不管用，必须设 `[Console]::OutputEncoding`：
>
> ```powershell
> [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
> ```
>
> Git Bash 不需要这一步。路径里的 `/` 两个终端都认，不用改。

```bash
cd ai-cs-evaluator
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
```

三行分别在干什么：

| 命令 | 作用 |
|---|---|
| `python -m venv .venv` | 建一个「虚拟环境」。说白了就是给这个项目单独开一个抽屉放依赖，不和系统里其他 Python 项目打架。`.` 开头表示隐藏文件夹 |
| `pip install -r requirements.txt` | 照着清单把要用的库都装上 |
| `-i https://mirrors.aliyun.com/...` | 用阿里云的镜像下载。国内直连官方源很慢，不加这个可能等到天荒地老 |

> 后面所有命令里的 `python`，都指 `.venv/Scripts/python.exe`。嫌长可以先激活环境
> （Windows 下执行 `.venv\Scripts\activate`），激活后直接敲 `python` 就行。

### 1.2 跑测试（最先做这个）

```bash
.venv/Scripts/python.exe -m pytest tests/ -q
```

**预期看到**：`37 passed`（37 个测试全部通过）。

为什么第一步就跑测试：测试是最快的「环境健康检查」。如果这里挂了，
后面所有命令都会挂，而你不用一个个去猜原因。测试全过，说明代码和依赖都是好的。

### 1.3 跑离线冒烟测试

```bash
.venv/Scripts/python.exe scripts/mock_run.py
```

**预期看到**：

```
链路自检
  轨迹条数            30
  平均轮数            2.0
  工具调用总数        30
  工具成功率          100.0%
  调用了判例检索      30 条
  过程标签分布        {'normal': 30}
[OK] 整条链路可跑通。
```

这一步在做的事：**它用一个假的模型，把整条链路完整跑了一遍**。

假模型是写死在 `scripts/mock_run.py` 里的 —— 它被设定成「先查一次判例库，
然后给一段固定回复」。所以这个脚本不需要联网、不花一分钱，就能验证
「测试执行器 → 轨迹落盘 → 过程指标 → 评测 Agent」这一整条路是通的。

它还顺手产出了 `output/traces.json`（30 条轨迹），格式和真跑出来的一模一样。
你可以先拿它把看板那些东西调通，不用等真跑完。

### 1.4 复现 v1 的基线

```bash
.venv/Scripts/python.exe -m src.analyze
```

**预期看到**：

```
  一致率            96.7%
  Cohen's Kappa     0.9231
  误伤（人对机偏）  [25]
```

这一步不需要 Key，因为它是拿 `output/` 目录里**已经存好的**评分结果在算。

为什么一定要先做这一步：**这个 96.7% / 0.9231 是整个项目的基准线**。
后面不管你怎么改代码，只要这个数字还是这个数字，就说明你没把原来的东西改坏。
一旦它变了，立刻停下来查 —— 大概率是你动了不该动的地方。

## 二、配好 Key 之后（这一步早晚要做）

### 2.1 把 Key 填进 .env

在项目根目录把 `.env.example` 复制一份，改名叫 `.env`（注意前面有个点），然后填：

```
LLM_API_KEY=sk-你的key
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

两件事要注意：

1. **`.env` 文件不会被提交到 Git**（`.gitignore` 里已经排除了）。
   这是底线 —— Key 泄漏是安全事故。
2. 想顺便启用向量检索的话，再填一个 `EMBED_API_KEY`（智谱的，有免费额度）。
   **不填也能跑**，检索会自动降级成纯 BM25，其他功能完全不受影响。

### 2.2 真跑一遍

```bash
# 先跑 3 条试水（省时间、省额度）
.venv/Scripts/python.exe -m src.eval.runner --limit 3

# 没问题了再跑满 36 条
.venv/Scripts/python.exe -m src.eval.runner

# 让评测 Agent 读轨迹打分，并和 v1 基线并排对比
.venv/Scripts/python.exe -m src.eval.judge
```

`src.eval.runner` 会打印每条用例的**一行摘要**，长这样：

```

```

从左到右分别是：用例编号、跑了几轮、耗时、结束原因、调了哪些工具。
这一行信息量很大 —— 一眼就能看出「它有没有调工具」「有没有转人工」。

## 三、按数据流读代码（不要按文件名读）

按文件名一个字母一个字母读，是最容易迷失的读法。**按数据流动的顺序读**，
每一步都知道「这个东西是哪儿来的、要拿去干嘛」。

### 第一层：先看数据长什么样（20 分钟）

打开 `data/processed/records.json`，看第一条：

```json
{
  "id": 1,
  "scene": "退款",
  "question": "转账转错了能退回来吗",
  "answer": "先让核对最近转账记录、选一笔订单，未直接回答转错能否退回。",
  "human_label": "答偏",
  "human_reason": "意图识别错",
  "human_note": "规则型问题被当成个人数据查询。应先给结论……",
  "machine": null
}
```

| 字段 | 含义 |
|---|---|
| `question` | 用户当时问的原话 |
| `answer` | **人工撰写的应答摘要**（注意：不是原始回复全文） |
| `human_label` | 人工判定：答对 / 答偏 |
| `human_reason` | 人工归的错因 |
| `human_note` | 人工写的分析：错在哪、应该怎么答 |
| `machine` | 留空，等机器评完回填 |

**这里有一个必须记住的细节：`answer` 是「摘要」不是「原文」。**

这个细节会反复出现，它至少解释了三件事：

- 为什么规则引擎里那条「模板复用」检测几乎抓不到东西（两条摘要措辞完全不同）
- 为什么这个项目的评测只能做到「二元判定可靠、错因归类不可靠」
- 为什么 v2 要自己造 Agent —— 因为手里只有摘要，没法评测原始回复的完整行为

### 第二层：v1 的评测链路（1 小时）

按这个顺序读：`loader.py` → `rules.py` → `prompts.py` → `llm_judge.py` → `analyze.py`

| 文件 | 一句话作用 | 读的时候重点看 |
|---|---|---|
| `loader.py` | 把 Excel 读成干净的 JSON | 开头注释里写的「三个坑」——为什么表头在第 3 行、为什么默认读不对 sheet |
| `rules.py` | 不调模型，纯代码打规则分 | `RULE_SPECS` 那张表，和文件头的「为什么只检测行为特征」 |
| `prompts.py` | 评分量表 | `RUBRIC` 常量，这是整个 v1 最需要「想清楚」的地方 |
| `llm_judge.py` | 调模型打分 | `extract_json`（容错解析）和 `judge_one`（重试） |
| `analyze.py` | 加权求和 + 算 Kappa | `cohen_kappa` 函数的注释 —— 那里用一个小例子讲清了 Kappa 到底在算什么 |

### 第三层：v2 的 Agent（2 小时）

按这个顺序读：`trace.py` → `retrieval.py` → `tools.py` → `cs_agent.py`

| 文件 | 一句话作用 | 读的时候重点看 |
|---|---|---|
| `trace.py` | 记录 Agent 每一步干了什么 | `Trace` 类里那几个 `@property`（`tool_names`、`failed_tools`、`guard_events`）—— 它们是评测的原料 |
| `retrieval.py` | 检索历史相似案例 | `tokenize` 怎么切中文、`search` 为什么强制要 `exclude_id` |
| `tools.py` | 5 个工具的「说明书 + 实现」 | `TOOL_SCHEMAS` 的描述怎么写、`dispatch` 怎么把异常变成可读信息 |
| `cs_agent.py` | ReAct 主循环 | `run` 方法里的 `for` 循环 —— 那是整个 Agent 的心脏 |

**读 `cs_agent.py` 的 `run` 方法时，记住它就是这四步在转圈**：

```
1. 把对话发给模型
2. 模型说「我要调工具」 → 执行工具 → 把结果塞回对话 → 回到第 1 步
   模型说「我答完了」   → 结束
3. 转人工了 → 收回工具权限 → 逼它说句收尾话 → 结束
4. 转到第 6 轮还在转 → 强制结束（防止死循环）
```

### 第四层：评测闭环（1 小时）

`eval/dataset.py` → `eval/runner.py` → `eval/metrics.py` → `eval/judge.py`

| 文件 | 一句话作用 |
|---|---|
| `dataset.py` | 定义「考什么、怎么算对、该有什么行为」 |
| `runner.py` | 把用例灌给 Agent，收轨迹，算过程指标 |
| `metrics.py` | 三个维度：任务完成率 / 工具调用准确性 / 满意度代理 |
| `judge.py` | 读轨迹打分，专抓「结果对但过程错」 |

### 现在可以先跳过的

下面这些，**第一遍不要读**。它们要么是锦上添花，要么需要先有前面的基础：

- `graph_agent.py` —— LangGraph 版，和 `cs_agent.py` 干的是同一件事，换个写法
- `hybrid.py` / `rerank.py` / `vector_store.py` —— 检索的进阶玩法
- `mcp_server.py` / `api/main.py` —— 服务化，和核心逻辑无关
- `report.py` —— 导出 Excel 的，纯工具代码

**但有一个例外**：读代码之前先要能说出这几个文件「大概在干什么、为什么要有」。
可以不会写，但不能不知道它们存在。

## 四、四个必须看懂的地方

这四处是这个项目里最值钱的设计。**如果只能记住四件事，记这四个。**

### 4.1 为什么规则引擎不匹配「未回答」这种词

`src/rules.py` 的注释里写着这段话，值得单独拎出来：

> 规则只检测**应答的行为特征**，不匹配「未回答」「未给出」这类结论词。
> 因为原始数据的 answer 字段是人工撰写的摘要，摘要里本来就写了人的判断。
> 如果规则去匹配这些词，等于拿人工的结论反推人工的标签 —— 那验证就失去意义了。

这段话在说什么：**如果你要用 A 去验证 B，那 A 就不能偷看 B 的答案。**

具体到这个项目：规则引擎是用来「验证」人工标注的。但如果规则去匹配
「未给出路径」这种词，而这个词本来就是人工写摘要时写进去的，那规则就不再是
独立判断了 —— 它变成了在抄人工的答案。这样算出来的一致率再高也没有意义。

**这段话怎么讲**：这是评测里的「数据泄漏」问题。同一个概念要验证两次时，
两次之间必须相互独立，否则数字好看但不可信。

### 4.2 Kappa 到底在算什么

打开 `src/analyze.py`，找到 `cohen_kappa` 函数，读它的注释。

核心就一句话：**Kappa 把「瞎猜也能蒙对」的部分扣掉。**

举个例子（也是注释里那个例子）：

- 30 条里有 21 条答对，那么一个「闭着眼睛全判答对」的傻瓜程序，准确率也有 70%
- 所以准确率高，不能证明程序聪明，可能只是它押中了多数类
- Kappa 就是把这个「押中多数类」带来的虚高扣掉

公式不用背，但要知道：**Kappa = 0 意味着「和瞎猜一样」，Kappa > 0.8 意味着
「几乎完全一致」**。

**这段话怎么讲**：为什么不报准确率？因为在我这个数据集上准确率会虚高。
我用 Kappa，是为了证明「扣掉运气成分后，机器判断仍然可信」。

### 4.3 一个不能省的参数：exclude_id

看 `src/agent/retrieval.py` 的 `search` 方法：

```python
def search(self, query, k=3, exclude_id, scene=None, min_score=0.0):
```

注意 `exclude_id` **没有默认值**。这是故意的。

为什么：判例库里装的是「答对的历史案例」，而测试集用的是同一批问题。
如果要评第 16 条，而第 16 条的标准答案正好在判例库里 —— 那 Agent 就是
把答案捞出来抄了一遍。这样跑出来的分数全是假的。

所以检索时必须把「正在评测的那一条自己」排除掉。给它设成必传参数，
就是让「忘了防泄漏」这件事在代码上不可能发生。

**这段话怎么讲**：这是评测系统里的数据泄漏。我把它做成了强制参数，
因为这种错误一旦发生，分数会变好看，而且不会报错 —— 是最难发现的那种 bug。

### 4.4 写操作为什么要有确认闸门

看 `src/agent/tools.py` 里的 `_tool_apply_refund`：

```python
if not user_confirmed:
    return {
        "ok": False,
        "error": "用户尚未确认，退款被拦截",
        "hint": "请先向用户复述订单号与金额，取得明确同意后再调用一次……",
    }
```

关键在这个闸门**放在哪一层**：

- 如果写在 prompt 里（「调用退款前必须先征求用户同意」），那它只是**建议**，
  模型注意力一偏就绕过去了
- 写在代码里，它就是**规则**，绕不过去

**这段话怎么讲**：Agent 里凡是会改变真实世界状态的操作（花钱、发货、改数据），
边界必须用代码守，不能用提示词守。提示词是软约束，代码是硬约束。

## 五、三个练习（从易到难）

光读不写，理解是假的。这三个练习做完，你才算真的上手。

### 练习 1：加一个规则检测器（30 分钟，最简单）

打开 `src/rules.py`，仿照 `R5 无实质内容`，加一个 `R6`：

> 检测「回答里出现了『请稍后』『正在处理』这类拖延话术」。

要改三个地方：

1. 写一个正则（模仿 `NO_SUBSTANCE_RE` 的写法）
2. 写一个 `detect_xxx` 函数（模仿 `detect_no_substance`）
3. 把它加进 `RULE_SPECS` 列表，想一个扣分数

改完跑 `.venv/Scripts/python.exe -m src.rules` 看结果变化。
**记得最后把扣分改回去或删掉** —— 否则 v1 的基线就变了。

### 练习 2：改 Agent 的行为准则（1 小时）

打开 `src/agent/cs_agent.py`，找到 `SYSTEM_PROMPT`。

它现在是 7 条准则。试着改第 3 条（关于前提条件的），或者加一条第 8 条。

改完跑：

```bash
.venv/Scripts/python.exe -m src.eval.runner --limit 5
```

看行为有没有变化。**这就是 prompt 工程的实际工作方式**：改一版 → 跑评测 → 看数字。

### 练习 3：给评测加一个指标（2 小时，最有价值）

打开 `src/eval/metrics.py`，现在的三个维度是：

- 任务完成率（`task_completion`）
- 工具调用准确性（`tool_call_accuracy`）
- 满意度代理（`satisfaction`）

试着加第四个维度，比如：**平均轮数**或者**转人工率偏高说明什么**。

模仿现有函数的写法就行。加完记得在 `build_report` 里调用它。

这个练习最有价值，因为「给评测加指标」正是 AI 应用岗要做的事。

## 七、几个常见的坑

**坑 1：改了代码，基线变了**

跑一下 `.venv/Scripts/python.exe -m src.analyze`，看还是不是 96.7% / 0.9231。
不是的话，检查你是不是动了 `rules.py` 的扣分权重或 `config.py` 里的 `WEIGHT_RULE`。

**坑 2：`ModuleNotFoundError: No module named 'src'`**

说明你不在项目根目录。所有 `python -m src.xxx` 命令都必须在
有 `README.md` 的那一层执行。

**坑 3：中文在终端里是乱码**

Windows 终端默认用 GBK。项目里的入口脚本都做了 UTF-8 处理
（`sys.stdout.reconfigure(encoding="utf-8")`），但你自己写的小脚本要手动加这一行。

**坑 4：改了 prompt 但结果没变**

`streamlit` 和部分模块有缓存。最稳的办法是关掉终端重新跑。

**坑 5：想不通某个设计为什么这样写**

先看那个文件的**开头注释**。这个项目里每一个「看起来奇怪」的写法，
文件头都写了理由 —— 这是刻意的，因为这些「为什么」正是最难答的部分。

## 八、最后一句

这个项目真正的价值不在「用了多少技术」，而在**每个地方都有取舍记录**:
为什么这样、为什么不那样、什么情况下会失效。

能说出「这个方案在什么情况下不成立」的人，
比能说出「这个方案多好」的人，可信度高得多。
