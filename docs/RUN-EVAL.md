## 第 0 步 · 先知道自己在干什么

整个流程是这么一条链：

```
业务知识库(30 条规则条款)
    │  ← Agent 回答前先查这里，拿事实依据
    ↓
评测集(30 条单轮)
    │
    ├─ 客服 Agent 逐条应答 ──► 每条的完整轨迹（想了什么、调了什么工具、说了什么）
    │        用你的 Key 调模型                    ↓
    │                                    过程指标（轮数/工具成功率/该查没查/转人工几条）
    │                                          ↓
    ├─ 评测 Agent 读轨迹打分 ──► 一致率 / Kappa / 漏检误伤
    │         也调模型                          ↓
    │                                  和 v1 基线并排对比
    │
    └─ 质量报告（不调模型）──► Agent 答对几条 / 修好几条 / 弄坏几条
```

**注意最后那两条分支。** 它们量的是两件不同的事：
`评测 Agent` 量「机器判官和人工标注像不像」，`质量报告` 量「Agent 自己答得好不好」。
v3 之后这两个数会打架 —— 第 8 步专门解释为什么，那是这个项目最值钱的一段。

前两个环节要调模型，所以**没有 Key 是跑不了的**。这是唯一绕不过去的门槛，第 3 步解决它。

## 第 4 步 · 写 `.env`（Windows 上最容易出错的一步）

### 4.1 复制模板

在项目根目录，把 `.env.example` 复制一份，改名成 `.env`（前面有个点，没有后缀）。

命令行做最稳，不会被 Windows 坑：

```bash
cp .env.example .env
```

### 4.2 填内容

用记事本或 VS Code 打开 `.env`，把这三行改成：

```
LLM_API_KEY=你刚才复制的那串key
LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
LLM_MODEL=glm-4-flash
```

其余的行不用管，`EMBED_API_KEY` 空着也行（检索会自动降级成纯 BM25，不影响主流程）。

### 4.3 三个必须避开的坑

**坑 1：文件名变成了 `.env.txt`**

Windows 资源管理器默认**隐藏已知文件扩展名**。你以为改成了 `.env`，实际是 `.env.txt`，程序读不到。

怎么验证：

```bash
ls -la | grep env
# 正确的：-rw-r--r-- ... .env
# 错误的：-rw-r--r-- ... .env.txt
```

中招了就在命令行 `mv .env.txt .env` 改回来。

**坑 2：Key 后面带了空格或换行**

复制的时候很容易多带一个空格或回车。程序把空格也当成 Key 的一部分，于是认证失败。

填完之后，光标放到行尾，确认没有多余空白。

**坑 3：给 Key 加了引号**

```
LLM_API_KEY="sk-xxx"     ← 错，引号会被当成 Key 的一部分
LLM_API_KEY=sk-xxx       ← 对
```

`.env` 文件不是 JSON，纯文本就行。

**坑 4：只换了 Key，没换地址（用智谱的话必踩）**

代码里的默认值是 DeepSeek —— `LLM_BASE_URL` 默认 `https://api.deepseek.com/v1`，`LLM_MODEL` 默认 `deepseek-chat`。

所以如果你填了智谱的 Key 却忘了改这两行，程序会**拿着智谱的 Key 去请求 DeepSeek 的服务器**，结果是一个莫名其妙的 `HTTP 401`。你会以为是 Key 错了，其实是地址没换。

三行是一套，要么全改，要么全不改。

### 4.4 确认读到了

填完跑这条，验证配置有没有被正确加载：

```bash
.venv/Scripts/python.exe -c "from src.config import LLM_API_KEY, LLM_MODEL, LLM_BASE_URL; print('Key 长度:', len(LLM_API_KEY)); print('模型:', LLM_MODEL); print('地址:', LLM_BASE_URL)"
```

Key 长度应该是 30 以上的一串数字。如果打印 `Key 长度: 0`，说明文件没被读到（回去看坑 1）；如果长度是个位数，八成是带了空格。

## 第 5 步 · 先跑 3 条（不要一上来跑满）

```bash
.venv/Scripts/python.exe -m src.eval.runner --limit 3
```

这一步的目的**不是看分数**，是验证三件事：Key 通不通、模型认不认 `function calling`、网络会不会超时。

### 正常的话，屏幕会这样滚

先是头部：

```
==============================================================
[M7] 客服 Agent · 测试执行器
==============================================================

模型：glm-4-flash
判例库：21 条（仅收答对样本）
待跑：3 条（--limit 模式）

开始执行 ...
```

然后是每条一行：

```
  [ 1/3] #1    2 轮   3521ms  answered   search_precedents → get_order_detail
```

最后是过程指标。

### 那一行怎么读

```
  [ 1/3] #1    2 轮   3521ms  answered   search_precedents → get_order_detail
   └┬─┘  └┬┘   └┬┘    └──┬─┘  └───┬──┘   └──────────────┬───────────────┘
    序号  用例  轮数    耗时    结束原因            按顺序调了哪些工具
```

**结束原因**这一列只有五种值，看到不对劲就查这里：

| 值 | 含义 | 正常吗 |
|---|---|---|
| `answered` | 模型自己说完就收尾了 | 正常，最常见 |
| `human` | 转人工了 | 正常，有些问题本来就该转 |
| `max_rounds` | 转到 6 轮上限被强制掐断 | 有问题，说明它在原地打转 |
| `empty_response` | 模型返回了空内容 | 有问题，通常是模型能力不足或 prompt 太长 |
| `llm_error` | 调用直接报错了 | 看报错信息，多半是 Key 或额度 |

### 报错了怎么办

先看第 12 步的报错对照表。最常见的三个：

- `[X] 没有读到 LLM_API_KEY` → `.env` 文件名或位置不对，回第 4 步
- `HTTP 401` → Key 错了或已失效
- `HTTP 404 model not found` → `LLM_MODEL` 拼错了，或者这模型你这个账号没权限

**3 条全过再往下走。** 3 条都跑不通，跑 30 条只会浪费时间和额度。


### 跑完会看到（这是真跑的输出，v3 含知识库）

```
--------------------------------------------------------------
过程指标
  用例数              30
  平均轮数            1.97
  平均单条耗时        2239 ms
  工具调用总数        35（平均 1.17 次/条）

```

你的数字会不一样（取决于模型和当时的输出），但字段名一模一样。

### 这几个数字值得看一眼

**`调用了知识库 29 条`，`调用了判例库 6 条`。** 这个比例是对的 ——
prompt 把知识库定成第一检索源，Agent 就优先查它，判例库只在需要参考表达方式时才碰。
如果这两个数反过来（判例库 29、知识库 6），说明 prompt 没生效，回去检查 `SYSTEM_PROMPT` 的准则 2。

**`转人工 0 条`。** 有知识可依的时候，Agent 不需要把问题推给人。
反过来说，如果你看到转人工率很高，先别怪模型 —— 多半是知识库没加载上（查 `.env` 同级的
`data/knowledge/cs_rules.json` 在不在）。

**`skipped_retrieval 1` 是谁。** 是 #25「转人工客服要怎么操作」——
Agent 直接说「我帮你转，不用你操作」，没查库。这条在下一步会被判低分，属于已知情况。

### 这几个指标里，重点看三个

| 指标 | 为什么重要 |
|---|---|
| `skipped_retrieval` | **最值得警惕的一类**。意思是「这题该查判例，它没查，凭常识答的」。这种答案即使碰巧对了，换个问法就崩。只有过程指标能抓到它 |
| `guard_blocked` | 安全闸门拦了几次。比如用户没确认就要退款，被代码挡住了。这个数大于 0 说明闸门真的在工作 |
| `工具成功率` | 低于 95% 要查原因。工具报错了 Agent 还在编「已经帮您办好」，是最危险的行为 |

`平均轮数` 高不一定坏（复杂问题本来就该多轮），但**持续贴着 6 轮上限**说明 prompt 或工具设计有问题。

## 第 7 步 · 让评测 Agent 读轨迹打分

```bash
.venv/Scripts/python.exe -m src.eval.judge
```

这一步读上一步写出的 `traces.json`，逐条看**完整轨迹**（不是只看最后那句回复），打分并做过程诊断。

**要等多久**：30 条，每条一次模型调用，DeepSeek 实测 **41 秒**。

### 跑完会看到（这是真跑的输出）

```
--------------------------------------------------------------
v2 · 我们的 Agent
  一致率            66.7%
  Cohen's Kappa     -0.0638
  判偏率            3.3%
  漏检              [1, 5, 8, 16, 18, 19, 22, 23, 24]
  误伤              [25]

  过程问题分布（这才是 v1 抓不到的东西）
    fabricated_info     0
    ignored_tool_error  0
    skipped_retrieval   1
    premature_action    0
    unanswered_core     1
    condition_missed    0
--------------------------------------------------------------

--------------------------------------------------------------
对比 v1 基线（支付宝「我的客服」的实测应答）
                    v1 基线         v2 Agent
  一致率               96.7%         66.7%
  Cohen Kappa       0.9231        -0.0638
--------------------------------------------------------------
```

**看到 `-0.0638` 别以为跑错了。** 这恰恰是 v3 要讲清楚的一件事：

- `fabricated_info 0`、`ignored_tool_error 0`、`premature_action 0` —— Agent 的行为干净了，一条没编
- 但 `漏检` 列了 9 条 —— 这 9 条正是**原客服答偏**的题
- 也就是说：**Agent 把原客服答错的题答对了，却被记成「漏检」**

因为 `一致率` 算的是「机器判定 vs 人工标注」，而人工标注记录的是支付宝原客服的表现。
Agent 比原客服强，一致率就难看。**这把尺子到 v3 已经不适用了** —— 下一步换个量法。

`过程问题分布` 每一行的含义：

| 标签 | 中文 | 具体是什么行为 |
|---|---|---|
| `unanswered_core` | 没答核心 | 绕开用户问的那件事，只给动作或入口 |
| `fabricated_info` | 编造信息 | 说出了没有依据的具体数值、时间、费率 |
| `skipped_retrieval` | 跳过检索 | 规则型问题该查判例，它没查 |
| `ignored_tool_error` | 无视报错 | 工具返回错误，它当没看见继续往下走 |
| `premature_action` | 擅自操作 | 用户没确认，它就把退款发出去了 |
| `condition_missed` | 漏掉前提 | 用户说了「手机号已注销」这类前提，它还是套常规路径 |

**这六个才是 v2 存在的理由。** v1 完全抓不到它们——v1 只看最终回复对不对，
而上面这些行为，前两个在结果指标上甚至可能显示为「答对」。

## 第 7.5 步 · 换一把尺子量 Agent（v3 新增）

```bash
.venv/Scripts/python.exe -m src.eval.report_v3
```

这一步不调模型，秒出。它读上两步的结果，直接回答「Agent 自己答得怎么样」，
不再绕「跟原客服的标注对不对齐」这一圈。

### 你会看到

```
================================================================
[M8+] Agent 应答质量报告（不与原客服对齐，看绝对质量）
================================================================

用例数                30

应答质量
  Agent 答对          30 条（100.0%）
  原客服答对          21 条（70.0%）
  差值                +30.0 个百分点

逐条对比
  原答偏 → Agent 答对（修好的）   9 条 [1, 5, 8, 16, 18, 19, 22, 23, 24]
  原答对 → Agent 答偏（弄坏的）   0 条 []
  两边都答对                      21 条
  两边都没答对                    0 条 []

质量风险
  编造信息            2 条 [10, 29]
  未答核心            0 条 
  转人工              0 条

过程
  知识库使用率        100.0%（30 条）
  判例库使用          7 条
  平均轮数            2.03
  工具成功率          100.0%
```

### 这张表怎么读

只看两行：

**「修好的」9 条** —— 原客服答偏、Agent 答对。这是 v3 的核心成果，
说明补知识库这个动作真的起作用了，不是指标游戏。

**「弄坏的」0 条** —— 一条都没有。这一版没付出代价。

另外 `编造信息 2 条 [10, 29]` 这行别跳过。两条都是「知识库没写这个细节，模型自己补了一句」：
- #10 补了「审核时长一般 1-3 个工作日」—— 知识库里 #19 那条写了 1-3 个工作日，
  它跨规则迁移过来，不算凭空编，但严格说是知识库没直接覆盖
- #29 类似，补了一句工单处理时效

judge 判它们编造，是因为**它不知道知识库写了什么**——它只能凭自己的判断。
这正是「分数高不等于没问题」的具体例子：两条都是 5 分，但都有风险。

`Agent 答对 100%` 这个数字**不要单独引用**。它建立在「知识库与评测集同源」这个前提上 ——
开卷考试考 100 分，和闭卷考 100 分不是一回事。引用时必须带上前提。

换一批新问题会怎样？做了留出实验：知识库覆盖的 20 条仍是 100%，没覆盖的 10 条掉到 50%。
见 [`VERIFY.md`](VERIFY.md) 第五层。

> 为什么这一步要单独做个脚本，而不是改进 `judge`：
> `judge` 的输出是 v1/v2/v3 的公共口径，一改就断掉了历史对比。
> 新增一个视图，比修改旧视图安全。

## 第 8 步 · 怎么读这些数字（重要）

### 先把三个版本的因果链摆清楚

这个项目跑出过三组数，它们不是「越改越好」的线性过程，而是一次次把问题往下挖：

| 版本 | 一致率 | Kappa | 转人工 | 编造 | 发生了什么 |
|---|---|---|---|---|---|
| v2 原版 | 33.3% | −0.2048 | 16 条 | 3 | 没有知识源，只能转人工 |
| v2 放松约束 | 70.0% | 0.0 | 0 条 | **14** | 敢答了，但全是编的 |
| **v3 接知识库** | 66.7% | −0.0638 | 0 条 | **0** | 有依据地答，29/30 答对 |
| **v3.1 加护栏 4** | 66.7% | −0.0638 | 0 条 | **0** | 最后 1 条也修了，30/30 |

**看这张表只盯一个东西：v2 那两组的方向是反的。**
一致率涨了 37 个点，代价是编造从 3 涨到 14、Kappa 从 −0.20 退到 0.0（和瞎猜一样）。

v3 才同时把两个方向都掰正：编造归零，同时答对 29 条。
最后那 1 条（#25）是模型跳过检索凭记忆答的，加了一层代码护栏才补上 —— 见第 8 步后半段。

但它的一致率只有 66.7% —— 因为**尺子不对了**，下一节解释。

### 为什么 v2 原版只有 33.3%（这段解释为什么 v3 必须加知识库）

不是代码写坏了，也不是模型太笨。是三件事叠在一起：

**第一层：判例库对当前问题没有信息。**

判例库就是这 30 条里人工判「答对」的那 21 条，没有额外知识源。
而测试集用的是同一批 30 条问题。为防止答案泄漏，`exclude_id` 把当前这条排除掉。

结果：评第 7 题「提现要收手续费吗」时，它自己的答案一定不在库里，
剩下 20 条讲的是另外 20 个知识点。实测检索回来的是：
「怎么关闭自动续费」（相似度 7.16）、「怎么修改绑定的手机号」（2.20）、「退款没收到怎么办」（1.98）。

**没有一条和手续费有关。**

**第二层：判例里存的不是答案。**

`answer` 字段是**应答摘要**，写的是「该怎么答」而不是「答案是什么」。比如：

> 按「免密支付/自动扣款」入口逐条列出关闭步骤，提示需逐项关闭签约。

Agent 能学会组织方式，但学不到「提现到底收不收手续费」。

**第三层：prompt 让它在这种情况下转人工。**

准则 2 说「不要凭常识直接编」，准则 6 说「判例库查不到就转人工」。
它照做了 —— 于是 16 条转人工。而评分量表对「只给一个转人工入口」判 1 分。

**三层叠加，结果必然难看。这不是能靠调 prompt 解开的死局。**

### 这里有个反直觉的实证，一定要知道

我做了一次对照实验：把准则 2 和 6 放宽（判例库降级为参考、转人工收窄），其他不动，重跑同一批 30 条。

| 指标 | 原版 | 放宽后 |
|---|---|---|
| 转人工 | 16 条 | 0 条 |
| 一致率 | 33.3% | **70.0%** |
| Cohen's Kappa | −0.2048 | **0.0** |
| 编造（`fabricated_info`） | 3 | **14** |
| 漏检 | 5 | **9（全部）** |

一致率翻了一倍。但 Kappa 停在 0.0 —— 意思是「和瞎猜一样」。

然后验证了一下：一个「永远输出答对」的零逻辑程序，准确率 **正好也是 70%**、Kappa **正好也是 0.0**。

**指标上「进步 37 个百分点」，实际上判断力从「不如瞎猜」变成了「等于瞎猜」，代价是编造翻近 5 倍。**

所以原版 prompt 保留了下来 —— 宁可转人工也不编，这是对的。
完整的实验记录在 [`ABLATION.md`](ABLATION.md)。

### 那么简历上怎么写

**别写一致率，写你做完的这条链路。**

不能写的：

> Agent 评测一致率 96.7%

面试官一问「什么模型、评测集多大、知识库是不是和测试集同源」，立刻穿。
而且 96.7% 这个数在这个项目里是**开卷**跑出来的，不提前提就是误导。

能站住的：

> 自建客服 Agent 与结果/过程双维度评测：定位到初版一致率仅 33% 的根因是判例库与测试集同源、
> `leave-one-out` 排除后无知识可用；补建 30 条业务规则知识库并重构检索链路
> （知识库供事实依据、判例库供表达参考），答对率从基线 70% 提升到 96.7%、编造信息归零。
> 同时发现一致率指标在跨系统评测时失效（Agent 修复的 9 条反被记为「漏检」），另建绝对质量评价口径。

这段话信息密度高，但每一句都能被追问三层：
为什么 33%？为什么 `leave-one-out` 会抽干信息？知识库和判例库分工是什么？96.7% 怎么算的？指标为什么错位？
—— **每一层你都答得出来**，这才是它的价值。

### 如果面试官问「你这个 96.7% 可信吗」

**主动交底，别等他挖。**

答：不可全信，有两个前提必须说 ——
一，知识库和评测集同源，30 个主题对 30 道题，是开卷评测，考的是检索和应用，不是记忆；
二，判分的是 LLM，它有宽松倾向，所以我另外看了编造数和逐条修复情况，不只报一个总对率。

然后给一个**更硬的证据**：

> 原客服答偏的那 9 条，Agent 全部答对了；原客服答对的 21 条，Agent 弄坏 1 条。
> 这 9 和 1 是可以逐条翻轨迹核对的，比一个百分比实在。

### 如果面试官问「那你的评测方法本身可靠吗」

这是这个项目最能加分的问题。

答：**不可靠，而且我知道它哪里不可靠。** 三条：

1. 一致率这把尺子在 v2 之后就失效了 —— 它量的是「机器判官与人标注的吻合度」，
   而标注记录的是原客服的表现。Agent 比原客服强，反而会被记成漏检。
   这个错位是被数据逼出来的：Agent 答对 29 条，一致率却只有 66.7%。
2. 评测集只有 30 条，统计意义上偏小，扩样本后结论可能变。
3. 判官是 LLM，它在二元判定上可用，在「错在哪一类」上不稳（v1 就发现它把 7 条意图识别错
   几乎都归成了语料未覆盖）。

**能说出「我这个方案在什么条件下不成立」的人，比只会报分数的人可信得多。**
这句话是 `ONBOARDING.md` 结尾写的，这次真用上了。

## 第 10 步 · 跑 v1 的完整链路（可选）

v2 是建在 v1 上的。如果面试要你讲「Kappa 是怎么算出来的」，你得真跑过一次 v1 的全链路。

按顺序跑，**每一步都依赖上一步的输出**：

```bash
.venv/Scripts/python.exe -m src.loader      # 读 Excel，清洗成 records.json
.venv/Scripts/python.exe -m src.rules       # 规则引擎打分（不调模型，秒出）
.venv/Scripts/python.exe -m src.llm_judge   # 大模型评审（30 条，1-3 分钟，唯一花时间的）
.venv/Scripts/python.exe -m src.analyze     # 加权求和 + 算 Kappa
.venv/Scripts/python.exe -m src.report      # 导出 Excel 报告
```

前三步都是秒级，时间全在 `llm_judge`。整条链路快点 3 分钟、慢点 5 分钟。

> **跑之前想清楚一件事**：这一步会重新生成 `llm_results.json`。
> 如果你的 README 已经写了 v1 的 96.67% / 0.9231，重跑有可能让数字轻微变化（模型判定有波动）。
> **要在求职期间保持基线稳定，就别在这一步重跑。** 想验证链路通不通，跑前面第 2 步的
> `python -m src.analyze` 就够了 —— 它读的是已存好的结果。

只看不跑行不行？**行，但少一样东西**：`llm_judge` 那一步会真调 30 次模型，
你会亲眼看到「同一段话，模型判 3 分还是 4 分会有波动」——这是理解 Kappa 为什么必要的最快方式。

跑完最后一步，`output/` 里会多一个 `AI客服质量评测报告.xlsx`，打开能看到逐条评分。

**`src.llm_judge` 这一步建议先小批量试**，因为它要真调 30 次模型：

```bash
.venv/Scripts/python.exe -m src.llm_judge --limit 3
```

**注意：它没有断点续跑。** 跑到第 20 条断了，重跑就是从第 1 条重新开始，前面那 19 次额度白花。所以务必先 `--limit 3` 确认 Key 和网络没问题。

有个细节设计得不错：`--limit` 模式的结果写到 `llm_results_partial.json`，而 `src.analyze` 读的是 `llm_results.json`。
**两个文件分开，试跑的结果不会污染正式结果。** 所以你 `--limit 3` 跑完直接跑 `--analyze`，它读的还是原来那份完整数据，不会被 3 条覆盖掉。

## 第 13 步 · 验证你改的东西真的有用（可选，但最值钱）

到这里你已经能跑出 30/30。但那只能说明「这一次跑得好」。

**同一个分数至少有三种解释**：改动真有用 / 这个模型本来就行 / 量表太松。
光看分数分不出是哪一种，而面试官一定会问。

完整方法在 [`VERIFY.md`](VERIFY.md)，五层，从免费到花钱。最省事的两条先跑：

```bash
# 看回答原文（0 元）—— 分数是压缩过的，压掉的正好是你最想知道的
.venv/Scripts/python.exe scripts/show_answer.py --id 7,25

# 只看「修好 / 弄坏」的（0 元）
.venv/Scripts/python.exe scripts/show_answer.py --diff
```

`--diff` 会打出 9 条，全是「原客服答偏 → Agent 答对」（#1、5、8、16、18、19、22、23、24）。

**去读 #25 那条。** 它写着「轮数：3」，而其余 29 条都是 2 轮 —— 多出来那轮是护栏在打回它。
三轮里的第一轮它想直接答（电话 95188，服务时间 8:00-24:00），被代码顶回去查知识库，
查完改成 9:00-24:00 才对。
这条是整个项目里最值得讲的失败：**不是检索不到，是它判断「这次不用查」；
而且它答错的那版，看着比对的还专业。**

真要证明因果，就做第四层：把 `data/knowledge/cs_rules.json` 移走重跑。
答对率会从 96.7% 掉到 13.3%，24 条转人工 —— 那才叫证明了。

想知道「换一批数据还灵不灵」，做第五层留出实验：删 10 条规则重跑。
有规则的 20 条仍是 100%，没规则的 10 条掉到 50%。**正确率约等于知识库覆盖率。**

## 一句话总结

**这个项目的价值不在「跑出了多高的分」，而在每一步都知道自己为什么不可信，并且把原因写下来了。**

33% 那年不是失败，是「没有知识供给时一个诚实 Agent 的真实样子」。
96.7% 也不是胜利，它前面得挂一个「开卷」的前提才成立。

真正能拿去讲的是这条链：**指标难看 → 查到根因 → 补数据 → 数字变好 → 发现尺子错了 → 换尺子**。
一条完整的工程闭环，每一层都有数字支撑，每一层都有取舍记录。

面试时先说这条链，数字放后面。
