## 第 0 步 · 先知道自己在干什么

整个流程是四个环节，像流水线：

```
评测集(30 条单轮)
    │
    ├─ 客服 Agent 逐条应答 ──► 每条的完整轨迹（想了什么、调了什么工具、说了什么）
    │        用你的 Key 调模型                    ↓
    │                                    过程指标（轮数/工具成功率/该查没查）
    │                                          ↓
    └─ 评测 Agent 读轨迹打分 ──► 一致率 / Kappa / 漏检误伤
              也调模型                    ↓
                                    和 v1 基线并排对比
```

两个环节都要调模型，所以**没有 Key 是跑不了的**。这是唯一绕不过去的门槛，第 3 步专门解决它。

**推荐用智谱，因为 GLM-4-Flash 目前是免费的**，这个项目跑一遍大概几十万 token，用免费的完全够。

### 3.3 一个安全提醒

Key 等于你账户的钱包。**不要发到聊天窗口、不要写进代码、不要提交到 Git**。

这个项目已经做对了一半：`.env` 在 `.gitignore` 里，不会被提交。剩下的一半靠你——别手滑粘到别处。

代价是：**GLM-4-Flash 比 DeepSeek 弱**，跑出来的 Agent 指标会差一些。这个差别在第 8 步会讲怎么处理。

## 第 4 步 · 写 `.env`（Windows 上最容易出错的一步）

### 4.1 复制模板

在项目根目录，把 `.env.example` 复制一份，改名成 `.env`（前面有个点，没有后缀）。

命令行做最稳，不会被 Windows 坑：

```bash
cp .env.example .env
```

### 4.2 填内容

用记事本或 VS Code 打开 `.env`，把这三行改成：

```
LLM_API_KEY=你刚才复制的那串key
LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
LLM_MODEL=glm-4-flash
```

其余的行不用管，`EMBED_API_KEY` 空着也行（检索会自动降级成纯 BM25，不影响主流程）。

### 4.3 三个必须避开的坑

**坑 1：文件名变成了 `.env.txt`**

Windows 资源管理器默认**隐藏已知文件扩展名**。你以为改成了 `.env`，实际是 `.env.txt`，程序读不到。

怎么验证：

```bash
ls -la | grep env
# 正确的：-rw-r--r-- ... .env
# 错误的：-rw-r--r-- ... .env.txt
```

中招了就在命令行 `mv .env.txt .env` 改回来。

**坑 2：Key 后面带了空格或换行**

复制的时候很容易多带一个空格或回车。程序把空格也当成 Key 的一部分，于是认证失败。

填完之后，光标放到行尾，确认没有多余空白。

**坑 3：给 Key 加了引号**

```
LLM_API_KEY="sk-xxx"     ← 错，引号会被当成 Key 的一部分
LLM_API_KEY=sk-xxx       ← 对
```

`.env` 文件不是 JSON，纯文本就行。

**坑 4：只换了 Key，没换地址（用智谱的话必踩）**

代码里的默认值是 DeepSeek —— `LLM_BASE_URL` 默认 `https://api.deepseek.com/v1`，`LLM_MODEL` 默认 `deepseek-chat`。

所以如果你填了智谱的 Key 却忘了改这两行，程序会**拿着智谱的 Key 去请求 DeepSeek 的服务器**，结果是一个莫名其妙的 `HTTP 401`。你会以为是 Key 错了，其实是地址没换。

三行是一套，要么全改，要么全不改。

### 4.4 确认读到了

填完跑这条，验证配置有没有被正确加载：

```bash
.venv/Scripts/python.exe -c "from src.config import LLM_API_KEY, LLM_MODEL, LLM_BASE_URL; print('Key 长度:', len(LLM_API_KEY)); print('模型:', LLM_MODEL); print('地址:', LLM_BASE_URL)"
```

Key 长度应该是 30 以上的一串数字。如果打印 `Key 长度: 0`，说明文件没被读到（回去看坑 1）；如果长度是个位数，八成是带了空格。

## 第 5 步 · 先跑 3 条（不要一上来跑满）

```bash
.venv/Scripts/python.exe -m src.eval.runner --limit 3
```

这一步的目的**不是看分数**，是验证三件事：Key 通不通、模型认不认 `function calling`、网络会不会超时。

### 正常的话，屏幕会这样滚

先是头部：

```
==============================================================
[M7] 客服 Agent · 测试执行器
==============================================================

模型：glm-4-flash
判例库：21 条（仅收答对样本）
待跑：3 条（--limit 模式）

开始执行 ...
```

然后是每条一行：

```
  [ 1/3] #1    2 轮   3521ms  answered   search_precedents → get_order_detail
```

最后是过程指标。

### 那一行怎么读

```
  [ 1/3] #1    2 轮   3521ms  answered   search_precedents → get_order_detail
   └┬─┘  └┬┘   └┬┘    └──┬─┘  └───┬──┘   └──────────────┬───────────────┘
    序号  用例  轮数    耗时    结束原因            按顺序调了哪些工具
```

**结束原因**这一列只有五种值，看到不对劲就查这里：

| 值 | 含义 | 正常吗 |
|---|---|---|
| `answered` | 模型自己说完就收尾了 | 正常，最常见 |
| `human` | 转人工了 | 正常，有些问题本来就该转 |
| `max_rounds` | 转到 6 轮上限被强制掐断 | 有问题，说明它在原地打转 |
| `empty_response` | 模型返回了空内容 | 有问题，通常是模型能力不足或 prompt 太长 |
| `llm_error` | 调用直接报错了 | 看报错信息，多半是 Key 或额度 |

### 报错了怎么办

先看第 12 步的报错对照表。最常见的三个：

- `[X] 没有读到 LLM_API_KEY` → `.env` 文件名或位置不对，回第 4 步
- `HTTP 401` → Key 错了或已失效
- `HTTP 404 model not found` → `LLM_MODEL` 拼错了，或者这模型你这个账号没权限

**3 条全过再往下走。** 3 条都跑不通，跑 30 条只会浪费时间和额度。

### 这一次跑出来的「转人工 16 条」值得停下来看一眼

30 条里有 16 条转人工，占 53%。而其中 **11 条人工标注是「答对」** ——
意味着这些题本来有标准答案，Agent 却推给了人。

原因不是它偷懒。往下看第 7 步和第 8 步，这是个更大的问题。

### 这几个指标里，重点看三个

| 指标 | 为什么重要 |
|---|---|
| `skipped_retrieval` | **最值得警惕的一类**。意思是「这题该查判例，它没查，凭常识答的」。这种答案即使碰巧对了，换个问法就崩。只有过程指标能抓到它 |
| `guard_blocked` | 安全闸门拦了几次。比如用户没确认就要退款，被代码挡住了。这个数大于 0 说明闸门真的在工作 |
| `工具成功率` | 低于 95% 要查原因。工具报错了 Agent 还在编「已经帮您办好」，是最危险的行为 |

`平均轮数` 高不一定坏（复杂问题本来就该多轮），但**持续贴着 6 轮上限**说明 prompt 或工具设计有问题。

## 第 7 步 · 让评测 Agent 读轨迹打分

```bash
.venv/Scripts/python.exe -m src.eval.judge
```

### 跑完会看到（这是真跑的输出）

```
--------------------------------------------------------------

  一致率            33.3%
  Cohen's Kappa     -0.2048
  判偏率            63.3%
  漏检              [1, 8, 16, 22, 24]
  误伤              [2, 4, 7, 10, 11, 12, 13, 14, 20, 21, 26, 27, 28, 29, 30]

  过程问题分布（这才是 v1 抓不到的东西）
    fabricated_info     3
    ignored_tool_error  0
    skipped_retrieval   1
    premature_action    0
    unanswered_core     19
    condition_missed    1
--------------------------------------------------------------

--------------------------------------------------------------
对比 v1 基线（支付宝「我的客服」的实测应答）
                    v1 基线         v2 Agent
  一致率               96.7%         33.3%
  Cohen Kappa       0.9231        -0.2048

```

**看到 `-0.2048` 别以为是自己跑错了。** 用原版代码、原版数据、DeepSeek 跑，
就是会得到这个数。原因在下一节，值得完整读一遍。

**Kappa 是负数是什么意思**：机器的判定比「随机按比例瞎猜」还要差。
注意是「比瞎猜还差」，不是「差一点」。

`过程问题分布` 每一行的含义：

| 标签 | 中文 | 具体是什么行为 |
|---|---|---|
| `unanswered_core` | 没答核心 | 绕开用户问的那件事，只给动作或入口 |
| `fabricated_info` | 编造信息 | 说出了没有依据的具体数值、时间、费率 |
| `skipped_retrieval` | 跳过检索 | 规则型问题该查判例，它没查 |
| `ignored_tool_error` | 无视报错 | 工具返回错误，它当没看见继续往下走 |
| `premature_action` | 擅自操作 | 用户没确认，它就把退款发出去了 |
| `condition_missed` | 漏掉前提 | 用户说了「手机号已注销」这类前提，它还是套常规路径 |

**这六个才是 v2 存在的理由。** v1 完全抓不到它们——v1 只看最终回复对不对，
而上面这些行为，前两个在结果指标上甚至可能显示为「答对」。

## 第 8 步 · 怎么读这些数字（重要）

### 33.3% 和负 Kappa 是怎么来的

这不是代码写坏了，也不是模型太笨。查下来是三件事叠在一起：

**第一层：判例库对当前问题没有信息。**

判例库就是这 30 条里人工判「答对」的那 21 条，没有额外知识源。
而测试集用的是同一批 30 条问题。为防止答案泄漏，`exclude_id` 把当前这条排除掉。

结果：评第 7 题「提现要收手续费吗」时，它自己的答案一定不在库里，
剩下 20 条讲的是另外 20 个知识点。实测检索回来的是：
「怎么关闭自动续费」（相似度 7.16）、「怎么修改绑定的手机号」（2.20）、「退款没收到怎么办」（1.98）。

**没有一条和手续费有关。**

**第二层：判例里存的不是答案。**

`answer` 字段是**应答摘要**，写的是「该怎么答」而不是「答案是什么」。比如：

> 按「免密支付/自动扣款」入口逐条列出关闭步骤，提示需逐项关闭签约。

Agent 能学会组织方式，但学不到「提现到底收不收手续费」。

**第三层：prompt 让它在这种情况下转人工。**

准则 2 说「不要凭常识直接编」，准则 6 说「判例库查不到就转人工」。
它照做了 —— 于是 16 条转人工。而评分量表对「只给一个转人工入口」判 1 分。

**三层叠加，结果必然难看。这不是能靠调 prompt 解开的死局。**

### 这里有个反直觉的实证，一定要知道

我做了一次对照实验：把准则 2 和 6 放宽（判例库降级为参考、转人工收窄），其他不动，重跑同一批 30 条。

| 指标 | 原版 | 放宽后 |
|---|---|---|
| 转人工 | 16 条 | 0 条 |
| 一致率 | 33.3% | **70.0%** |
| Cohen's Kappa | −0.2048 | **0.0** |
| 编造（`fabricated_info`） | 3 | **14** |
| 漏检 | 5 | **9（全部）** |

一致率翻了一倍。但 Kappa 停在 0.0 —— 意思是「和瞎猜一样」。

然后验证了一下：一个「永远输出答对」的零逻辑程序，准确率 **正好也是 70%**、Kappa **正好也是 0.0**。

**指标上「进步 37 个百分点」，实际上判断力从「不如瞎猜」变成了「等于瞎猜」，代价是编造翻近 5 倍。**

所以原版 prompt 保留了下来 —— 宁可转人工也不编，这是对的。
完整的实验记录在 [`ABLATION.md`](ABLATION.md)。

### 那么简历上怎么写

**别写一致率，写你发现了什么。**

不能写的：

> Agent 评测一致率 95%

面试官一问「什么模型、评测集多大、判偏率多少、Kappa 多少」，立刻穿。

能站住的：

> 对自建客服 Agent 做结果与过程双维度评测，发现单一准确率指标会失效：
> 放宽约束后准确率从 33% 升到 70%，但 Kappa 归零、编造信息从 3 条涨到 14 条。
> 据此要求所有结论以 Kappa 而非准确率呈现，并补充编造 / 跳过检索 / 无视工具报错等过程指标。

这段话里有数字，但数字是用来**支撑一个判断**的，不是用来炫耀的。
而且它讲的是一个完整的「发现问题 → 定位原因 → 改指标」链路 —— 面试官会顺着问下去，
你每一层都答得出来。

### 如果面试官问「那你这个 Agent 到底行不行」

老实说：**在当前数据条件下测不出可信结论，原因已经定位清楚。**

然后把第一层的那个死局讲一遍 —— 判例库和测试集同源、`exclude_id` 排掉了唯一有用信息、
判例存的是摘要不是答案。最后说修法：需要一份独立于测试集的知识源（真实规则文档 / 完整客服 SOP）。

**能说出「我这个方案在什么条件下不成立」的人，比只会报分数的人可信得多。**
这句话是 `ONBOARDING.md` 结尾写的，这次真用上了。

## 第 9 步 · 把数字填进 README

**这一步已经做过了。** README 的「v2 跑出来是什么样」一节现在有实测数据
（两轮对照 + Kappa 归零的实证），`docs/ABLATION.md` 是完整记录。

```markdown
| 指标 | 数值 |
|---|---|
| 转人工 | x 条（x%） |
| 一致率 | x% |
| Cohen's Kappa | x.xxxx |
```

## 第 10 步 · 跑 v1 的完整链路（可选）

v2 是建在 v1 上的。如果面试要你讲「Kappa 是怎么算出来的」，你得真跑过一次 v1 的全链路。

按顺序跑，**每一步都依赖上一步的输出**：

```bash
.venv/Scripts/python.exe -m src.loader      # 读 Excel，清洗成 records.json
.venv/Scripts/python.exe -m src.rules       # 规则引擎打分（不调模型，秒出）
.venv/Scripts/python.exe -m src.llm_judge   # 大模型评审（30 条，1-3 分钟，唯一花时间的）
.venv/Scripts/python.exe -m src.analyze     # 加权求和 + 算 Kappa
.venv/Scripts/python.exe -m src.report      # 导出 Excel 报告
```

前三步都是秒级，时间全在 `llm_judge`。整条链路快点 3 分钟、慢点 5 分钟。

> **跑之前想清楚一件事**：这一步会重新生成 `llm_results.json`。
> 如果你的 README 已经写了 v1 的 96.67% / 0.9231，重跑有可能让数字轻微变化（模型判定有波动）。
> **要在求职期间保持基线稳定，就别在这一步重跑。** 想验证链路通不通，跑前面第 2 步的
> `python -m src.analyze` 就够了 —— 它读的是已存好的结果。

只看不跑行不行？**行，但少一样东西**：`llm_judge` 那一步会真调 30 次模型，
你会亲眼看到「同一段话，模型判 3 分还是 4 分会有波动」——这是理解 Kappa 为什么必要的最快方式。

跑完最后一步，`output/` 里会多一个 `AI客服质量评测报告.xlsx`，打开能看到逐条评分。

**`src.llm_judge` 这一步建议先小批量试**，因为它要真调 30 次模型：

```bash
.venv/Scripts/python.exe -m src.llm_judge --limit 3
```

**注意：它没有断点续跑。** 跑到第 20 条断了，重跑就是从第 1 条重新开始，前面那 19 次额度白花。所以务必先 `--limit 3` 确认 Key 和网络没问题。

有个细节设计得不错：`--limit` 模式的结果写到 `llm_results_partial.json`，而 `src.analyze` 读的是 `llm_results.json`。
**两个文件分开，试跑的结果不会污染正式结果。** 所以你 `--limit 3` 跑完直接跑 `--analyze`，它读的还是原来那份完整数据，不会被 3 条覆盖掉。

## 第 11 步 · 打开看板（可选，5 分钟）

```bash
.venv/Scripts/python.exe -m streamlit run app.py
```

浏览器会自动打开 `http://localhost:8501`。

**看板上最值得玩的一步**：拖左侧「规则分权重」滑块。

拖到 1.0 是纯规则，拖到 0.0 是纯大模型。所有指标实时重算，因为分数早就落盘了，调权重不用重新调模型。

拖动的时候盯住一致率和 Kappa 的变化——你会看到某一个位置它们开始掉。
那个位置就是「规则和大模型各自贡献了多少」的答案。这是面试可以讲的东西。

## 第 12 步 · 报错对照表

| 你看到的 | 真实原因 | 怎么修 |
|---|---|---|
| `ModuleNotFoundError: No module named 'src'` | 不在项目根目录 | `cd` 到有 `README.md` 的那一层 |
| `[X] 没有读到 LLM_API_KEY` | `.env` 没被读到 | 检查文件名是不是 `.env.txt`、位置是不是项目根目录 |
| `HTTP 401 Unauthorized` | Key 错 / 失效 / 多了空格 | 重新复制一次 Key，注意行尾不要留空白 |
| `HTTP 404 model not found` | 模型名拼错，或账号没这个模型权限 | 智谱用 `glm-4-flash`，DeepSeek 用 `deepseek-chat` |
| `HTTP 429` | 触发限流 | 代码有退避重试，会自动等。连续 429 就隔几分钟再跑 |
| `HTTP 400 response_format` | 模型不支持强制 JSON 输出 | 调用 `chat()` 时传 `force_json=False`，或换模型 |
| 中文输出全是乱码 | 终端编码是 GBK | 换 PowerShell；或先执行 `chcp 65001` |
| `streamlit: command not found` | 没用 venv 的 python | 用 `.venv/Scripts/python.exe -m streamlit run app.py` |
| 改了 prompt 但结果没变 | 有缓存 | 关掉终端重开，最稳 |
| 跑一半断了 | 网络抖动 / 额度用完 | 看 `llm_error` 那几条的报错原文，额度用完就去控制台看余额 |

## 一句话总结

**这个项目的价值不在「跑出了多高的分」，而在「它知道自己在什么情况下不可信」。**

`unanswered_core`、`fabricated_info`、`skipped_retrieval` 这些标签，比任何一个百分数都更能说明你懂 Agent 评测。
面试时先说这些，数字放后面 —— 尤其当那个数字是 33.3% 的时候。
