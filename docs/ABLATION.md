# 消融实验：约束强度换来了什么

> 这是 README「还没做的」里那条「消融实验」的第一次落地。
>
> 起因很朴素：第一次把 v2 跑起来，一致率 33.3%、Kappa −0.2048。
> 一个负数 Kappa 意味着机器的判定比瞎猜还差。要么代码写错了，要么设计有问题。
> 查下来是后者，而且问题比「代码写错了」更值得记。

---

## 一、问题现象

用原版 `SYSTEM_PROMPT` 跑 30 条单轮用例，跑完让评测 Agent 打分：

```
v2 · 我们的 Agent
  一致率            33.3%
  Cohen's Kappa     -0.2048
  判偏率            63.3%
  漏检              [1, 8, 16, 22, 24]
  误伤              [2, 4, 7, 10, 11, 12, 13, 14, 20, 21, 26, 27, 28, 29, 30]

  过程问题分布
    unanswered_core     19
    fabricated_info      3
    skipped_retrieval    1
    condition_missed     1
```

`unanswered_core` 19 条 —— 近三分之二的答案是「没正面回答用户的问题」。
顺着这个线索查，30 条里有 **16 条转人工**（53.3%）。

而转人工的这 16 条里，有 **11 条人工标注是「答对」** —— 也就是说，这些题本来是有标准答案的，Agent 却把它推给了人。

---

## 二、根因：判例库对当前问题没有信息

挑一条最典型的看。第 7 题：

```
问：提现要收手续费吗
```

Agent 第一步调 `search_precedents`，检索返回：

| 相似度 | 检索回来的题 | 场景 |
|---|---|---|
| 7.16 | 怎么关闭自动续费 | 改单 |
| 2.20 | 怎么修改绑定的手机号 | 改单 |
| 1.98 | 退款显示成功但没收到怎么办 | 退款 |

**没有一条和「手续费」有关。** 第一条相似度 7.16 看着不低，但语义上八竿子打不着。

这不是检索算法坏了。原因在设计：

1. **判例库就是这 30 条里人工判「答对」的那 21 条**，没有额外的知识源。
2. 测试集用的是**同一批 30 条问题**。
3. 为了防答案泄漏，`search()` 的 `exclude_id` 是必传参数，评第 N 条时会把第 N 条自己排除掉。

三步叠加的结果是：**评任何一条时，它自己的答案一定不在库里，而剩下的 20 条讲的是另外 20 个知识点。**

更麻烦的是第二层：判例库里存的 `answer` 字段是**应答摘要**，不是答案本身。
比如「怎么关闭自动续费」存的是：

> 按「免密支付/自动扣款」入口逐条列出关闭步骤，提示需逐项关闭签约。

这是**对「该怎么答」的描述**，不是「答案内容」。Agent 能从中学会组织方式，但学不到「提现手续费到底收不收」。

所以 Agent 面对的是一个死局：**要么转人工，要么凭空编。**

## 三、那次对照实验

原版 prompt 里两条准则把 Agent 逼向了「转人工」：

```
2. 规则类问题必须先查判例库。……不要凭常识直接编。
6. 不确定就转人工。判例库查不到……调用 transfer_to_human。
   宁可转人工，也不要编一个听起来很合理的答案。
```

把这两条放宽（判例库降级为「参考口径」、转人工收窄到「需核实本人账户 / 涉及资金处置 / 超出业务范围」），
其他一个字不动，重跑同一批 30 条。

### 结果对比

| 指标 | A · 严格（原版） | B · 宽松（改后） |
|---|---|---|
| 转人工 | 16 条（53.3%） | **0 条** |
| 平均轮数 | 2.5 | 1.9 |
| 工具调用 | 45 次（1.5/条） | 27 次（0.9/条） |
| 调用了判例检索 | 29 / 30 | 27 / 30 |
| 一致率 | 33.3% | **70.0%** |
| Cohen's Kappa | −0.2048 | **0.0** |
| 判偏率 | 63.3% | **0.0%** |
| 误伤（机器冤枉正确） | 15 条 | 0 条 |
| 漏检（机器放过缺陷） | 5 条 | **9 条（全部）** |
| `fabricated_info` | 3 | **14** |
| `unanswered_core` | 19 | 0 |

### 这张表里最要命的一行

一致率从 33% 涨到 70%，看起来是巨大进步。**但 Kappa 从 −0.20 变成了 0.0。**

Kappa = 0 的意思是「和瞎猜一样」。为什么？因为放宽后 Agent 全部作答、评测 Agent 也全部判「答对」——
30 条判了 30 条对，机器的判定没有任何区分度。

于是做了一个对照验证：

```
一个「只会输出答对」的零逻辑程序
    → 准确率 70%（= 21/30，押中多数类）
    → Kappa   0.0
```

**和改词之后那个 Agent 的指标一模一样。**

也就是说：指标上「进步了 37 个百分点」，实际上 Agent 的判断力从「不如瞎猜」变成了「等于瞎猜」，
而代价是编造信息从 3 条涨到 14 条、9 条真实缺陷全部漏检。

---

## 四、三条结论

### 1. 准确率在这个场景下会骗人，而且不是理论上会

README 里写过一段：「30 条里 21 条答对，一个永远输出答对的傻瓜程序准确率也有 70%」。

写那段话时它是个论证用的假设。这次实验把它变成了**实测数据**：那个傻瓜程序真的跑出 70%，Kappa 真的是 0。

这也是为什么 `src/analyze.py` 里坚持报 Kappa 而不是准确率 —— 不是方法论上的洁癖，是踩过。

### 2. 提高指标和保持诚实是真冲突，不是可以两全的

宽松版把一致率翻了一倍，代价是编造从 3 条涨到 14 条。这不是调参失误，是同一个旋钮的两端：

- 约束紧 → Agent 不敢答 → 转人工率 53% → 指标难看，但**它没有编**
- 约束松 → Agent 敢答 → 指标好看，但**一半答案是编的**

在客服场景里，「编造一个听起来合理的收费标准」比「转人工」危险得多。所以这一版**保留了原版 prompt**，
把宽松版留作对照数据，不作为默认行为。

### 3. 真正的修法不在 prompt，在数据

两个极端都源于同一个前提错误：**把判例库和测试集当成同一批数据**。

`exclude_id` 防住了答案泄漏，这没错 —— 不排除的话分数会好看得离谱且毫无意义。
但防住泄漏之后，判例库对当前问题就只剩「组织方式的参考」，没有「事实的供给」。

要真正解决，只有一条路：**引入独立于测试集的知识源**。
比如真实的该平台规则文档、完整的客服 SOP，或者人工撰写的事实性答案（而不是「应答摘要」）。
把 `answer` 从「该怎么答」换成「答案是什么」，Agent 才有东西可依。

这件事当时没做，因为它需要一份看起来这个项目手上没有的数据。写在这里，是因为它比任何一个分数都重要。

## 四之二、后续：v3 把这条路走完了

上面这段写完几小时后，这件事做了 —— 因为「手上没有数据」这个判断，有一半是错的。

重看 `records.json` 才发现：**`answer` 字段里其实带着事实口径**。比如第 4 条不是「该怎么答」的空话，
而是写着「快速转出当日到账（日限 1 万元）、普通转出 T+1 个交易日」。这些是能直接用的知识。

于是做了三件事：

1. 把 30 条实测记录里的口径提炼成 30 条**业务规则条款**（`data/knowledge/cs_rules.json`），
   按主题组织、剥掉「这道题怎么答」的叙述，只留规则本身。
2. 新增 `search_knowledge` 工具，接进 Agent，并在 prompt 里定为第一检索源。
3. **把「知识」和「案例」彻底分开**：知识库给事实依据，判例库只给表达方式。
   知识库不参与 `leave-one-out` —— 它不是测试集的一部分。

结果：

| 指标 | v2 原版（严格） | v3（接知识库） | v3.1（加护栏 4） |
|---|---|---|---|
| Agent 答对 | — | 29 / 30（96.7%） | **30 / 30（100%）** |
| 知识库使用率 | — | 96.7%（29 条） | **100%（30 条）** |
| 与原客服一致率 | 33.3% | 66.7% | 66.7% |
| `fabricated_info` | 3 | **0** | **0** |
| 转人工 | 16 | **0** | **0** |

**原客服答偏的那 9 条，Agent 全部答对了**（#1、5、8、16、18、19、22、23、24）。

v3 只弄坏了 1 条：**#25「转人工客服要怎么操作」**。这条值得单独说，因为它是 v3.1 那个护栏的来源。

一开始我把它归成「量表盲点」——量表写了「只给转人工入口判 1 分」，没考虑用户诉求本来就是转人工的情形。
后来把工具链打出来才看清：

```
#25  转人工客服要怎么操作
工具：（没调工具）   轮数：1
转人工可以直接在这里帮你转，不用你自己操作。
```

**它一轮就答了，压根没查知识库。** 而知识库里有「如何转人工客服」这条规则，检索得分 48.39，
排在全库中上。查一下就能照着答。

所以这不是检索能力问题，是**判断失误**：在它的自我认知里，「转人工」是它自己的动作，不用查资料。

这个模式的隐蔽之处在于所有指标都不报错 —— 工具调用 0 次，成功率仍是 100%，只有把工具链打出来才看得见。

#### 改 prompt 之后，它答得「更好」了，然后错得更隐蔽

先试的是软办法：给 prompt 加第 8 条（分清「问怎么做」和「让你去做」）。结果：

```
转人工有两种方式：
1. 电话：拨打该平台客服热线，按语音提示转人工（服务时间 8:00–24:00）。
2. 在线：在该平台 App 里点「我的」→「我的客服」…
```

**judge 给了 5 分，30/30。** 但工具链还是 0 次调用 —— 它凭记忆答的。
而知识库里写的是「对话页点转人工按钮，**9:00-24:00**」。它答成了 8:00。

**分数涨了，事实反而错了。** 这是整个项目里最值钱的一课：
`skipped_retrieval` 才是警报，分数不是。

所以加了**护栏 4**（代码层）：模型第一轮没查任何资料就想直接答时，打回一次，要求先检索。
只打回一次 —— 硬拧三次会把它拧成复读机。实测触发 1 次，#25 变成 3 轮，
查到了 9:00-24:00 那条规则，照着答，才是真的答对。平均轮数只从 1.97 涨到 2.03。

一个必须同时说的代价：**一致率只涨到 66.7%，Kappa 还是负的（−0.0638）**。
不是没改好，是这把尺子已经不该用来量 Agent 了 —— 原因见下一节。

### 所以 v2 那个 33.3% 到底说明了什么

说明的是「**没有知识源时，一个诚实的 Agent 只能转人工**」。
它不是 Agent 能力的上限，是数据供给的下限。

这个区分很重要。只说「我的 Agent 一开始只有 33%」是自曝其短；
说「我定位到 33% 的根因是知识供给缺失，补了知识库后答对率到 96.7%；
剩下的 1 条查出来是模型跳过检索凭记忆答，又补了一层代码护栏到 30/30，
但发现一致率这把尺子本身错位，于是换了评价体系」—— 这是完整的工程判断。

### 尺子为什么错了

`一致率` 衡量的是「机器判官与人工标注的吻合度」。人工标注记录的是**原客服**的表现。

Agent 把原客服答偏的 9 条答对了 → 机器判「答对」→ 与标注「答偏」不符 → 记成**漏检**。

**Agent 表现越好，一致率越难看。** 这个指标在 v1 里是对的（评的是同一批回复），
搬到 v2/v3 就失效了（评的是另一个系统的回复）。

所以 v3 加了一份「绝对质量报告」（`python -m src.eval.report_v3`），
直接看 Agent 自己答对多少条、原客服答错的修好了几条、原客服答对的弄坏了几条。
不再绕「与人标注对齐」这一圈。

## 四之三、第三组：把知识库拿走

上面那个 96.7% 有个致命的解释漏洞：**它可能跟知识库没关系。**

v3 同时改了三样东西 —— 新建知识库、加 `search_knowledge` 工具、改 prompt 让 Agent 先查规则。
三个一起改，分数涨了，但不能说功劳是知识库的。也许是 prompt 改得更会说话了，
也许是这个模型本来就答得出这些题（deepseek-v4-flash 训练语料里该平台的常见问题不少）。

要排除这个解释，只有一个办法：**只动一个变量。**

### 怎么做的

把 `data/knowledge/cs_rules.json` 改个后缀，让代码找不到它：

```bash
mv data/knowledge/cs_rules.json data/knowledge/cs_rules.json.bak
```

代码一行没改，prompt 一个字没动，模型没换，测试集没换。
先确认 `KnowledgeBase()` 真的会抛 `FileNotFoundError`（跑到一半才发现没真正禁掉，就白跑了），
然后重跑 `runner` → `judge` → `report_v3`。

### 结果

| 指标 | v3 有知识库 | 拿掉知识库 | 变化 |
|---|---|---|---|
| **Agent 答对** | **29 / 30（96.7%）** | **4 / 30（13.3%）** | −25 条 |
| 转人工 | 0 | **24 条（80%）** | +24 |
| 未答核心（`unanswered_core`） | 1 | **25** | +24 |
| 工具成功率 | 100% | **64.6%** | −35.4pt |
| 平均轮数 | 1.97 | **3.5** | +1.5 |
| 修好（原客服答偏→Agent 答对） | **9** | 2 | −7 |
| 弄坏（原客服答对→Agent 答偏） | 1 | **19** | +18 |
| 编造信息 | 0 | 2 | +2 |
| 与原客服一致率 | 66.7% | 30.0% | −36.7pt |

**答对率从 96.7% 掉到 13.3%。** 同一份代码、同一个模型、同一句 prompt。

### 掉下去的过程值得看一眼

拿掉知识库后，Agent 并没有「变笨」——它还是在努力查。29 条用例里它尝试调 `search_knowledge` 29 次，
每一次都失败，错误信息是同一句：

```
知识库未加载
```

29 次失败正好等于 `tool_calls_failed: 29` 和 `tool_success_rate: 64.6%` 的分子。

然后它的行为链条是这样的：

1. 查知识库 → 失败
2. 改查判例库 → 能查到，但判例只有「这道题该怎么答」的叙述，没有事实口径
3. prompt 准则 2 说「不要凭常识编」→ 它守住了，没有编
4. 准则 6 说「查不到就转人工」→ 24 条转人工

**这不是能力退化，是数据供给断了之后，一个诚实的 Agent 唯一能做的事。**

它跟 v2 那个 33.3% 是同一个病：没有事实来源，只能推给人。
区别只是 v2 里判例库还有一点点残留信息（33.3%），这次连那点都没有（13.3%）。

### 这一组实验顺手暴露了一个指标 bug

跑完第一版对照，`agent_metrics.json` 里赫然写着：

```
知识库使用率        96.7%（29 条）
```

**知识库文件已经被移走了，显示使用率 96.7%。**

原因在统计口径：原来写的是「这条会话的 `tool_names` 里有没有 `search_knowledge`」——
`tool_names` 只记调用过什么，不记成功没有。Agent 每轮都尝试查，每次失败，
名字还是进了列表，于是「用过」成立。

已经改成只数成功的（`src/eval/runner.py` 的 `_used_ok()`）：

```python
def _used_ok(trace: Trace, tool: str) -> bool:
    return any(c.get("name") == tool and c.get("ok") for c in trace.tool_calls)
```

新口径下三组数据：

| 组 | 知识库成功调用 | 判例库成功调用 |
|---|---|---|
| v3（有知识库） | 29 | 6 |
| 无知识库 | **0** | 29 |
| 原版 prompt（还没知识库） | 0 | 29 |

`0` 才是这一组该有的数。

这件事的教训比实验本身更值得记：**一个只会涨的指标，比没有指标更危险。**
它不报错、不告警，只在你想验证自己没错的时候，告诉你「你没错」。

### 现在的结论

96.7% 的因果链是干净的：

```
知识库存在 → Agent 查得到事实口径 → 敢答 → 答对 29 条
知识库不存在 → Agent 查不到 → 守住「不编」→ 转人工 24 条 → 答对 4 条
```

只有一步之遥是没验的：**知识库的质量。** 这 30 条规则是我从实测记录里提炼的，
如果提炼时把某条口径写错了，Agent 会自信地答错，而上面所有指标都看不出来。
要验这个，得拿真实客服文档逐条对，那是另一件事。

## 四之四、第四组：留出实验（换一批数据还灵不灵）

前三组都在同一批 30 条上打转。这一组回答另一个问题：**知识库没覆盖时，Agent 会怎样。**

### 为什么做这个

30/30 是开卷的 —— 30 条规则从 30 条实测记录里提炼，一问一答对得上号。
这个数字好看，但它答不了最自然会问的那句：「换一批数据还能这样吗？」

### 怎么做

删掉 10 条规则（按场景分层：退款 3、改单 2、账户 2、服务 3），其余一律不动，重跑 30 条。

被删规则对应的 10 个问题 = 留出集，另外 20 条 = 对照组。

### 结果

| 组 | 条数 | 答对 | 通过率 |
|---|---|---|---|
| 对照组（有规则） | 20 | **20** | **100%** |
| 留出集（无规则） | 10 | **5** | **50%** |

留出集失败的 5 条：

| 问题 | 得分 | 失败方式 |
|---|---|---|
| #5 自动续费扣的钱能退吗 | 1 | 转人工 |
| #7 提现要收手续费吗 | 1 | 转人工 |
| #11 怎么更换绑定的银行卡 | 1 | 转人工 |
| #19 实名认证审核要多久 | 1 | 转人工 |
| #27 被盗刷的钱多久能追回 | 3 | 答了，但没给时长 |

### 三条结论

**1. 正确率 ≈ 知识库覆盖率。**
Agent 的贡献是「有依据就忠实执行」，不是「知道答案」。给什么答什么，给错了它照样自信地答。

**2. 未覆盖时 4/5 转人工。**
这是护栏和准则 6 在起作用 —— 它没有编。但用户的问题没解决，在客服指标里这仍然是失败。

**3. #27 那一类最危险。**
它答了，有处理路径、有操作步骤，但没给关键数字（追回时长），得 3 分。
比转人工危险，因为看起来像解决了。

它的原话值得抄下来：

> 知识库里没有「盗刷资金追回时长」的明确规则条款，我不能凭常识给你一个具体天数，
> 所以先说明处理路径，再帮你转人工核实。

**它明说了「知识库没有」。** 只看得分你永远不知道这件事，读原文才知道：
它没编，只是没依据。这两种失败要分开处理 —— 前者改 prompt，后者补数据。

### 顺带否掉一个想法

原本想用检索得分当「覆盖率指标」：得分低 = 没覆盖，自动标出来。

做出来发现不行。留出实验的实测：

| 问题 | 删规则后得分 | 命中主题 | 结果 |
|---|---|---|---|
| #25 转人工客服要怎么操作 | **10.46** | 实名信息填错 | **答对了** |
| #5 自动续费扣的钱能退吗 | **30.23** | 关闭自动续费 | **答错了** |

10.46 分的答对了，30.23 分的答错了。BM25 算的是字面相似，算不出「是不是同一件事」。

所以 `scripts/kb_coverage.py` 只做一件事：把问题和命中的主题排成一张表，让人看。
分数只用来决定「要不要多展开几个备选」，不用来判定。

## 五、附带发现的两个问题

### 问题 1：runner 只跑了 30 条，不是 36 条

`src/eval/dataset.py` 的 `build_all()` 返回 **36 条**（30 条单轮 + 6 条多轮），
但 `src/eval/runner.py` 直接读 `records.json` 的 30 条，**没有调用 `build_all()`**。

所以那 6 条多轮用例虽然定义了、有测试、进了 README 的「36 条评测集」，
但**从来没有被真正执行过**。

这是文档与代码的不一致，被问到时很尴尬。已知，未修。

### 问题 2：评测 Agent 自己也会矛盾

第 28 条同时拿到了「5 分」和 `fabricated_info=true`。

打分和过程标记是两条独立的判断链，前者看「答得完不完整」，后者看「有没有编」。
所以会出现「答得漂亮但是编的」这种组合 —— 这本身不算 bug，反而说明过程指标有必要。
但它也意味着：**不能只看 score，必须两个一起看。**

## 六、怎么复现

三组实验的共同点：**每次只动一个变量。**

```bash
# 组 A：原版 prompt（严格约束，无知识库）
git checkout <v2 那个 commit>   # 或按第三节描述把准则 2、6 改回去
.venv/Scripts/python.exe -m src.eval.runner
.venv/Scripts/python.exe -m src.eval.judge

# 组 B：同 A，但把准则 2、6 放宽
.venv/Scripts/python.exe -m src.eval.runner
.venv/Scripts/python.exe -m src.eval.judge

# 组 C：v3 原样，只把知识库文件移走
mv data/knowledge/cs_rules.json data/knowledge/cs_rules.json.bak
.venv/Scripts/python.exe -m src.eval.runner
.venv/Scripts/python.exe -m src.eval.judge
.venv/Scripts/python.exe -m src.eval.report_v3
mv data/knowledge/cs_rules.json.bak data/knowledge/cs_rules.json

# 组 D：v3 原样（有知识库）—— 就是默认跑法
.venv/Scripts/python.exe -m src.eval.runner
.venv/Scripts/python.exe -m src.eval.judge
.venv/Scripts/python.exe -m src.eval.report_v3
```

**跑之前先把结果存一份**，否则下一组会覆盖。要备份的是四个文件：

```
output/traces.json
output/agent_metrics.json
output/agent_judge_results.json
output/agent_quality_report.json
```

本次三组的原始数据留在 `output/working/ablation/`（`*-oldprompt.json` / `*-v3.json` / `*-noKB.json`），
可以直接拿来做对比，不必重跑。

**注意**：`scripts/mock_run.py` 会覆盖 `traces.json`，别在两组实验之间跑它。

更细的五层验证方法（含不花钱的静态检查、怎么看回答原文、留出实验）见 [`VERIFY.md`](VERIFY.md)。
