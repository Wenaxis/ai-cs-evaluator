# AI 客服质量评测台

给 AI 客服的应答做自动化质量评测的工具。输入问答记录，输出逐条评分、错因归因和一致性验证报告。

用 **规则引擎 + 大模型评审** 混合评分，并以人工标注为基准验证机器的判定有多可信。

> **v2 已改造完成**：项目从「评测工具」升级为「AI 客服 Agent + 评测闭环」。  
> 新增了一个能自己调工具、能多轮、会失败的客服 Agent，再用 v1 的评测能力反过来测它。  
> 详见文末「v2：从「评测工具」变成「Agent + 评测」」一节。**v1 的全部链路原样保留，指标未被改动。**

> **第一次读这个项目？先看 [`docs/ONBOARDING.md`](docs/ONBOARDING.md)。**  
> 那里面有：从零跑起来的完整步骤（分「不需要 Key」和「需要 Key」两段）、

## 核心结论

在 30 轮真实实测问答上（支付宝「我的客服」）的评测结果：

| 指标                | 数值                      |
| ----------------- | ----------------------- |
| 评测轮数              | 30                      |
| 人工标注              | 答对 21 / 答偏 9（答偏率 30.0%） |
| 人机判定一致            | 29 / 30                 |
| 一致率               | **96.67%**              |
| **Cohen's Kappa** | **0.9231**              |
| 漏检（机器放过真实缺陷）      | 0 条                     |
| 误伤（机器冤枉正确答案）      | 1 条                     |

Kappa 0.9231 按业界通用口径属「几乎完全一致」，意味着扣除「押中多数类」的虚高成分后，机器判定仍与人工标注高度吻合。

> 为什么不直接报准确率：30 条里 21 条答对，一个「永远输出答对」的傻瓜程序准确率也有 70%。Kappa 把「瞎猜也能蒙对」的部分扣掉，剩下的才是工具真实的判断力。

## 为什么需要混合评分

单用任一种方法都不够，这一点由数据证明：

**规则引擎单独跑**：一致率 96.7%，但**漏掉了第 23 条**。  
第 23 条是「账户解冻需要提供什么材料」被答成与上一轮雷同 —— 典型的模板复用缺陷。  
规则用文本相似度检测，但原始数据的应答字段是**摘要**而非全文，两条摘要措辞完全不同，相似度算出来很低。**纯规则抓不住语义问题。**

**大模型评审单独跑**：能识别出第 23 条的语义问题，但判定有波动，且错因归类不稳定。

**合起来跑**：一致率 96.67%，漏检归零。

## 方法设计

### 评分分档（5 分制）

| 分数 | 判据                               |
| -- | -------------------------------- |
| 5  | 直接回答核心诉求，且给出完整口径（分档 / 时长 / 具体路径） |
| 4  | 回答了核心诉求，但口径不完整                   |
| 3  | 部分相关，但答的不是用户问的那件事                |
| 2  | 转向其他话题或动作（如直接让用户查订单）             |
| 1  | 答非所问，或只给一个转人工入口                  |
| 0  | 拒答、答错                            |

判定遵守的硬规则：**不因礼貌、详细、语气好而加分；不因「查了用户账户」算答对**——查账户只是动作，不是回答。

### 规则引擎的 5 类检测器

| 规则       | 判据                       | 扣分  |
| -------- | ------------------------ | --- |
| R1 导流甩锅  | 把规则型问题推给「查订单 / 看记录」等操作环节 | 2.6 |
| R2 缺时间口径 | 问了时效，回答里没有任何具体时间         | 2.2 |
| R3 缺操作路径 | 问了怎么操作，答里没有可照做的路径或入口     | 1.8 |
| R4 模板复用  | 与上一轮回答文本相似度 > 0.8        | 2.4 |
| R5 无实质内容 | 没作答，或直接甩人工入口             | 2.6 |

**关键设计决策**：规则只检测可观测的**行为特征**，不匹配「未回答」「未给出」这类结论词。因为原始数据的应答字段是人工撰写的摘要，摘要里本来就写了人的判断——如果规则去匹配这些词，等于拿人工的结论反推人工的标签，验证就失去意义了。

### 混合公式

```
最终分 = 0.4 × 规则分 + 0.6 × 大模型分
最终分 ≥ 3.5 → 判「答对」，否则「答偏」
```

两个权重和阈值都可在界面上实时调整。

## 快速开始

### 1. 环境

需要 Python 3.10 以上。

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
```

> 国内网络建议加镜像：`-i https://mirrors.aliyun.com/pypi/simple/`

### 2. 配置 API Key

复制 `.env.example` 为 `.env`，填入大模型 API Key：

```
LLM_API_KEY=sk-xxxxxxxx
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

默认适配 DeepSeek（OpenAI 兼容接口）。换成智谱只需改这三行：  
`LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4` + `LLM_MODEL=glm-4-flash`。  
**代码不用动** —— 配置与逻辑分离。

### 3. 按顺序运行

```bash
python -m src.loader       # 读取并清洗原始数据
python -m src.rules        # 规则评分
python -m src.llm_judge    # 大模型评审（约 1-3 分钟）
python -m src.analyze      # 混合评分 + 一致性验证
python -m src.report       # 导出 Excel 报告
```

### 4. 打开可视化看板

```bash
streamlit run app.py
```

浏览器访问 `http://localhost:8501`。

**看板上最有价值的一步**：拖动侧栏的「规则分权重」滑块。拖到 1.0 是纯规则、拖到 0.0 是纯大模型，所有指标实时重算——因为分数已落盘，调整权重不需要重新调用大模型接口。

## 已知局限

1. **评测集规模小**：30 条真实人工实测样本，统计意义上偏小。方法可复现，扩充数据后结论应更稳健。
2. **数据是应答摘要而非全文**：影响了模板复用检测（R4）的有效性，也限制了对多轮上下文的判断。
3. **错因归类不稳定**：大模型在「答对/答偏」的二元判定上可靠（Kappa 0.92），但在「错在哪一类」上明显弱于人工——它把 7 条「意图识别错」几乎都归成了「语料未覆盖」。
4. **评分量表的盲点**：评分量表写了「只给转人工入口判 1 分」，但没考虑**用户诉求本身就是转人工**的情形——这种情况下给出入口就是正解。第 25 条「转人工客服要怎么操作」属于这一类。
   **补充**：v3 里这条被判 1 分其实判对了——Agent 连入口都没给，只说了「我帮你转，不用你操作」，而且它压根没查知识库。详见文末「v3」一节。

第 4 条已在文末列出，属可修正项：在量表里增加前置判断，若用户诉求即为转人工，给出入口即为正解。

## v2：从「评测工具」变成「Agent + 评测」

### 为什么改

v1 有一件事做得很扎实：它证明了「一套评测方法本身到底可不可信」—— 用 Kappa 0.9231 讲清了机器的判定和人工的判定有多吻合。

但它有个天花板：**它评的是别人家客服的应答摘要**。离线、单轮、被动。想再往前走，唯一的路是自己造一个 Agent 出来，再把这套评测能力反过来指向它。

v2 就是这一步。

### 新增了什么

| 模块                       | 干什么               | 对应的能力            |
| ------------------------ | ----------------- | ---------------- |
| `src/agent/retrieval.py` | 判例检索（BM25）        | RAG              |
| `src/agent/tools.py`     | 5 个工具的 schema 与实现 | function calling |
| `src/agent/cs_agent.py`  | ReAct 主循环 + 三层护栏  | Agent 编排         |
| `src/agent/trace.py`     | 执行轨迹落盘            | 可观测性             |
| `src/llm_client.py`      | 统一模型调用层           | 基础设施             |
| `src/runner.py`          | 测试执行器 + 过程指标      | 自动化回归            |
| `src/judge_agent.py`     | 评测 Agent：读轨迹打分    | LLM-as-Judge     |

### 三个值得单独说的设计

**一、判例检索强制 leave-one-out。**

判例库来自「人工判定为答对」的样本，测试集用的又是同一批问题。评第 N 条时如果不把第 N 条自己从检索池里排除，Agent 就是把答案捞出来抄一遍 —— 评测数字会好看得离谱，而且毫无意义。

所以 `search()` 里的 `exclude_id` 是必传参数，不给默认值。**让「忘了防泄漏」这件事在代码上不可能发生。**

**二、写操作的确认闸门放在工具层，不放在 prompt 层。**

退款和改地址必须 `user_confirmed=true` 才会执行。这个判断写在代码里而不是提示词里，理由很直白：

> prompt 是建议，模型心情不好就绕过去了；代码才是规则。

**三、评测标准沿用 v1 的量表，一个字没改。**

标准不变，v1 和 v2 的分数才能直接对比。**同一把尺子，量支付宝的客服，也量我们自己造的 Agent** —— 尺子一换，对比就作废了。

### v2 才有的指标

v1 只有「最终答案对不对」一个维度。v2 还能回答：平均几轮收口、调了几次工具、工具成功率多少、安全闸门拦了几次、该查判例时查了没有、一共烧了多少 token。

**为什么要过程指标**：一个 Agent 可能「答对了，但过程完全是错的」—— 比如它压根没查判例、凭常识蒙对了答案。这种正确换个问题就崩，但在结果指标上完全看不出来。

### 怎么跑

```bash
# 0. 先离线验证链路通不通（不需要 Key，不花额度）
python scripts/mock_run.py

# 1. 单元测试
python -m pytest tests/ -v

# 2. 让 Agent 跑测试集，收轨迹 + 过程指标
python -m src.eval.runner --limit 3      # 第一次先跑 3 条试水
python -m src.eval.runner                # 跑满 30 条单轮

# 3. 评测 Agent 读轨迹打分，并与 v1 基线对比
python -m src.eval.judge

# 3.5 看 Agent 的绝对应答质量（v3：不与原客服对齐，换一把尺子）
python -m src.eval.report_v3

# 4. 起 HTTP 服务（接口文档在 http://127.0.0.1:8000/docs）
uvicorn src.api.main:app --reload --port 8000

# 5. 作为 MCP Server 启动，供 Claude Desktop / Cursor 等客户端接入
python -m src.mcp_server
```

### 跑出来是什么样（v2 原版，未接知识库）

> **这两组数据是 v2 阶段跑的，那时 Agent 还没有知识库。当前代码已是 v3，直接跑会得到下一节的结果。**
> 保留在这里，是因为它最能说明「没有知识供给时，一个诚实的 Agent 会变成什么样」。

在 30 条单轮用例上真跑（`deepseek-chat`）。实测消耗：runner 单轮约 **10 万 token / 95 秒**，
评测 Agent 再跑一遍约 40 秒。下表是两轮对照：

| 指标 | 原版约束 | 放宽约束后 |
|---|---|---|
| 转人工 | 16 条（53.3%） | 0 条 |
| 一致率 | 33.3% | 70.0% |
| **Cohen's Kappa** | **−0.2048** | **0.0** |
| 误伤 / 漏检 | 15 / 5 | 0 / 9 |
| `fabricated_info`（编造） | 3 | 14 |

**这张表里最该看的是 Kappa，不是一致率。** 放宽约束后一致率翻了一倍，Kappa 却停在 0.0 —— 意思是「和瞎猜一样」。

验证过：一个「永远输出答对」的零逻辑程序，准确率也是 70%、Kappa 也是 0.0，和改词后的 Agent 指标完全相同。
代价是编造从 3 条涨到 14 条、9 条真实缺陷全部漏检。

所以**保留了原版约束**（宁可转人工也不编），把宽松版留作对照数据。
完整的现象、根因和结论写在 [`docs/ABLATION.md`](docs/ABLATION.md)。

**一个必须说明的局限**：判例库就是这 30 条里判对的 21 条，`exclude_id` 排除当前条之后，
剩下的 20 条讲的是另外 20 个知识点。加上判例里存的是「应答摘要」而非答案本身，
Agent 在库外问题上没有事实可依 —— 要么转人工，要么编。这个死局不是 prompt 能解的，
需要一份独立于测试集的知识源。见 `docs/ABLATION.md` 第四节。

> 另：`dataset.build_all()` 定义了 36 条（30 单轮 + 6 多轮），但 `runner.py` 直接读
> `records.json` 的 30 条，那 6 条多轮用例尚未接入执行器。这是已知的未完成项。

| 评测任务集构建                 | 30 条单轮已接入执行器；另 6 条多轮已定义但未接入（见下方说明） | `src/eval/dataset.py`             |
| 任务完成率 / 工具调用准确性 / 用户满意度 | 三个维度全部实现                           | `src/eval/metrics.py`             |
| 数据清洗                    | v1 的 loader 保留，另加评测集构建             | `src/loader.py`                   |

### 两个版本并存，是刻意的

手写版回答「你懂不懂原理」，LangGraph 版回答「你会不会用工业界的工具」。  
面试这两个问题都会问，而且是两个不同的问题。相关测试在 `tests/test_graph_agent.py`  
—— 两个版本跑同一套断言，保证「换个编排方式」不等于「换了个 Agent」。

LangGraph 在这里的价值也说清楚：**不是少写代码**（声明式状态机其实更长一点），  
而是流程图可见、能挂 checkpointer 断点续跑、新人看代码看的是节点和边。  
框架解决的是「流程可见性和可恢复性」，不是「写起来更短」。

### 一个诚实的说明

**向量检索在 21 条语料上的效果并不比 BM25 强，甚至可能更差。**  
上它的理由不是「它现在更好」，而是：判例库会长大，以及检索被抽象成了一层可替换的东西。  
这个取舍写在 `src/agent/vector_store.py` 的文件头。面试被问到「为什么用向量库」时，  
照实说比硬夸有效。

### 还没做的（下一步）

- **看板的 v2 页面**：回归对比视图还没做（`app.py` 目前还是 v1 的看板）
- **消融实验**：已经做了三组 —— 约束强度 A/B、开关知识库。完整数据见 [`docs/ABLATION.md`](docs/ABLATION.md)，
  验证方法（四层，从免费自检到控制变量）见 [`docs/VERIFY.md`](docs/VERIFY.md)。
  还没做：换模型（同一句 prompt 换 GLM / Qwen 跑一遍）、关掉重排、关掉向量召回
- **评测集扩充**：多轮用例目前 6 条，且 **`runner` 还没消费它们**（只读 `records.json` 的 30 条），
  `dataset.build_all()` 返回的 36 条里那 6 条从来没真跑过 —— 已知，未修
- **judge 本身的可靠性**：judge 也是大模型，它给 5 分不等于真是 5 分。
  彻底的做法是人工复核 20 条算人与 judge 的 Kappa，没做
- **延迟与成本基线**：`/chat` 单次响应时间与 token 成本还没有系统实测。
  跑 30 条整轮的参考值是：`runner` 82 秒 / 总 token 约 10.6 万，`judge` 41 秒

## v3 · 补上知识供给，Agent 才真能干活

### 为什么要有 v3

v2 跑出来一致率 33.3%、Kappa −0.2048，30 条里 16 条转人工。查下来不是模型笨，是**它没有地方可查**：

- 判例库就是测试集里判对的 21 条，为防抄答案强制 `leave-one-out` 排除当前条
- 排除之后，剩下的 20 条讲的是另外 20 个知识点
- 判例里存的是「应答摘要」，写的是怎么答，不是答案是什么
- 于是 Agent 只有两条路：转人工，或者凭空编

完整归因在 [`docs/ABLATION.md`](docs/ABLATION.md)。

### 做了什么

把「知识」和「案例」拆成两层：

| 层 | 存什么 | 作用 | 防泄漏 |
|---|---|---|---|
| 知识库 `data/knowledge/cs_rules.json` | 30 条业务规则条款 | 回答的事实依据 | 不参与 leave-one-out |
| 判例库（原有） | 21 条历史问答 | 参考表达方式 | 强制排除当前条 |

新增 `src/agent/knowledge.py`（BM25 检索，复用原有分词）和 `search_knowledge` 工具，
prompt 里定为第一检索源：**先查知识库 → 没有再看判例 → 都没有才转人工**。

一个刻意的取舍：**不给相关度硬阈值**。BM25 分数在 30 条语料上没有绝对意义，
与其拍一个魔数把可能答对的问题误判成「无知识」，不如把分数和条款一起交给模型判断相关性。

### 结果

| 指标 | v2 原版 | v3 |
|---|---|---|
| Agent 答对 | — | **29 / 30（96.7%）** |
| 原客服答对（基线） | 21 / 30（70%） | 21 / 30（70%） |
| 转人工 | 16 条 | **0 条** |
| `fabricated_info`（编造） | 3 条 | **0 条** |
| 知识库使用率 | — | 96.7%（29 条） |
| 平均轮数 | 2.5 | 1.97 |

**原客服答偏的 9 条，Agent 全部答对了**（#1、5、8、16、18、19、22、23、24）。
唯一没答对的是 #25「转人工客服要怎么操作」—— Agent 说「我帮你转，不用你操作」，被量表判「只给入口」得 1 分。

一开始我把这条归因成「量表的已知盲点」（见「已知局限」第 4 条）。后来把工具链打出来才发现不是：

```
#25  转人工客服要怎么操作
工具：（没调工具）   轮数：1
```

**它一轮就答了，压根没查知识库。** 而知识库里有一条「如何转人工客服」，检索得分 48.39，
排在全库中上 —— 只要查一下就能照着答。

所以这条的失败是**判断失误，不是检索能力问题**：在它的自我认知里，「转人工」是它自己的动作，
不需要查资料。量表判「未答核心」其实判对了。

这种失败模式比「检索不到」更值得记 —— 检索不到是能力上限，能查到却不查是判断失误，
后者所有指标都不报错，只有把工具链打出来才看得见。

### 但一致率只到了 66.7%，Kappa 还是负的

**因为那把尺子不该用来量 Agent 了。**

`一致率` 算的是「机器判定与人工标注的吻合度」，而人工标注记录的是**支付宝原客服**的表现。
Agent 把原客服答偏的 9 条答对了 → 机器判「答对」→ 与标注不符 → 记成**漏检**。

**Agent 表现越好，一致率越难看。** 这个指标在 v1 里完全成立（评的是同一批回复），
搬到 v2/v3 就失去了意义（评的是另一个系统的回复）。

所以 v3 加了一份独立的绝对质量报告：

```bash
python -m src.eval.report_v3
```

它直接回答三个问题：Agent 自己答对多少条、原客服答偏的修好了几条、原客服答对的弄坏了几条。
不再绕「与人标注对齐」这一圈。指标错位的完整论证见 `docs/ABLATION.md` 第四之二节。

### 一个必须说在前面的局限

**知识库和评测集同源**：30 个主题对应 30 道题，内容提炼自实测记录的口径。
这是**开卷评测** —— 考的是「能不能检索到、对不对得上号」，不是「记不记得住」。

真实产品里知识库本来就该独立于用户提问；这里因为只有这一份数据，
只能做到「形式上独立（规则条款 vs 问答对）、来源上同源」。
被面试问到时主动讲这一点，比被对方问出来好。

其中 9 条（原客服答偏、无正确口径）是按通用业务规则补充的，文件里用 `source` 字段区分
`measured` 和 `supplemented`，可以逐条核对。

### 这些数字是怎么验的

96.7% 至少有三种解释：改动真有用 / 这个模型本来就行 / 量表太松。光看分数分不出是哪一种。

四层逐层排除，从最便宜的开始：

| 层 | 做什么 | 花多久 | 结论 |
|---|---|---|---|
| 一 | `scripts/selfcheck.py` 静态自检 18 项 | 3 秒 | 代码状态符合预期（并当场抓到一处注释撒谎） |
| 二 | `scripts/show_answer.py` 读回答原文 | 5 分钟 | 三样齐全：结论先行 / 分档 / 例外 |
| 三 | `runner` → `judge` → `report_v3` 重跑 | 3 分钟 | 答对 29，编造 0，工具成功率 100% |
| 四 | **移走知识库重跑** | 5 分钟 | **答对率 96.7% → 13.3%，24 条转人工** |

第四层才把「相关」变成「因果」：同一份代码、同一个模型、同一句 prompt，只差一个 JSON 文件。

完整命令、真实输出和判读标准见 [`docs/VERIFY.md`](docs/VERIFY.md)。

## 数据来源

30 轮实测记录来自对支付宝「我的客服」（蚂蚁智服）的人工测试，覆盖退款、改单、物流、催件四类场景，全部为通用规则类问题，不依赖具体订单号。人工标注结果与错因分类由人工逐条判定，作为本项目的验证基准。
